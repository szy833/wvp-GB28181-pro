用户授权继续下一步。本轮先复测单路，不做并发阶梯，不修改 WVP/ZLM 运行配置、不重启服务、不删除设备或录像、不提交 Git、不操作 `t.cap`。

候选文件：`tools/gb28181-load-test/bin/gb28181-load-test-candidate-20261011`，SHA-256 为 `69e0a4068b9a39df1ba5cedda0328ccb6b26cb76798502e31832c21ea2f5c432`。

计划依次执行：

1. 只读预检运行版本、监控、媒体基线、设备编号和磁盘。
2. 一台新虚拟设备完成注册/目录，指定该测试设备 TCP-PASSIVE，重复点播和 HTTP 停止；结束时仍在播放的会话验证主动 BYE。使用短时 FFmpeg RTSP 解码检验输出。
3. TCP 功能及资源清理通过后，使用另一个新编号验证 UDP 路径。
4. 前述链路通过后，单路不拉取媒体，观察无人观看关闭和资源回收。
5. 单路保持观看超过媒体文件的 30 秒周期，检验循环播放是否连续可解码。

同一时刻仅一台本轮虚拟设备运行、最多一路媒体。新测试编号使用 `370200000011106` 段，通道使用 `370200000013106` 段；执行前确认无既有记录，后续阶段不复用前阶段身份。既有真实设备及历史测试设备不在操作范围。

凭据由运行服务读取后只写入本机权限 0600 的 `.private.yaml`，不输出到公开报告。信令采集只保存测试身份的 SIP 方法、CSeq、Call-ID、tag、SSRC，不保存 Authorization、密码或原始报文。

原始证据目录：`tools/gb28181-load-test/reports/retest-20261011/`。实际步骤、结果和发现的问题在每阶段结束后追加。

## 阶段 1：TCP 重复点播及主动退出

执行命令（项目根目录）：

```bash
python3 tools/gb28181-load-test/reports/retest-20261011/probe.py tcp-repeat --index 0 --watch
```

步骤：

1. 启动一台新设备 `37020000001110600001`，完成 Digest 注册和 Catalog；WVP 显示在线、通道数 1。
2. 只修改这台测试设备的传输方式为 TCP-PASSIVE，宽限期后按 0.1 次/秒调度点播，最多一路，成功后保持 8 秒再停止。
3. 每 2 秒独立查询媒体/listener/SIP 会话及工具指标；每个新媒体实例用 FFmpeg RTSP 解码，保存进度及错误日志。
4. 55 秒时取消工作负载；最后一个仍在播放的 dialog 由设备主动 BYE，保留 SIP 接收直到响应完成。
5. 等候工具生成报告，并再次独立确认资源回收。被动信令采集晚于进程启动，覆盖后续 INVITE/ACK/BYE，不声称覆盖首次注册全过程。

实际结果（11:11:43–11:13:09）：

- 点播 4/4 成功，HTTP 停止 3/3 成功，最后一个会话主动 BYE 1/1 成功，无 BYE 拒绝或超时。
- INVITE、200、ACK 的 CSeq/Call-ID 匹配，例如 `325 INVITE` 与 `325 ACK`；主动 BYE Request-URI 正确，WVP 返回 `200 OK`，不再是此前的 400。
- 实际 RTP 794 包、833952 字节，发送错误 0。RTSP 输出采样约 33976 字节/秒，与低码率输入相符，不再是此前单路约 120Mbps。
- 点播实际延迟约 172–180ms，HTTP 停止约 28–34ms；报告分位数使用近似桶值，不能替代这些原始延迟。
- 每次停止后资源归零，再次点播成功；最终媒体/listener/API 可见 SIP 会话均为 0。整机可用磁盘变化约 7.3MiB，不将全部变化归因于本测试录像。
- FFmpeg 四次退出码均为 0，但每次均有 DTS 不单调错误。因此仅确认能解码出帧，不认定媒体时间轴及播放质量通过。
- 工具报告为 INCONCLUSIVE：除资源监控缺失外，WVP 会话结构及 ZLM 空 listener 响应不兼容，清理等待满 30 秒。

证据：`tcp-repeat.json`、`.details.csv`、`.samples.jsonl`、`.probe.json`、`.wire.jsonl`、`.decode-*.log`、`.decode-*.progress`。

## 已发现的问题（持续补充）

### P1：真实媒体输出时间轴仍异常

TCP/UDP RTSP 解码均出现 `Application provided invalid, non monotonically increasing dts`，例如 `15 >= 1` 重复约 198 次。请求解码 3 秒，进度只到 `00:00:00.640000`，尽管已解码 202 帧。

同一个本机 PS 文件直接经 FFmpeg 解码可得到 75 帧、3 秒，且无该错误。差异位于工具发送到 ZLM 再输出 RTSP 的链路，暂不能直接归因于 WVP。需继续核查 PES/RTP 时间轴和 ZLM 对输入 PS 的解析兼容性；在此之前停止并发阶梯。

### P2：清理监控不兼容现场 API 响应

- WVP `/api/play/ssrc` 实际为 `data: {data: [], count: 0}`，工具按数组解析报 `invalid WVP session data`。
- ZLM `listRtpServer` 在空列表时返回成功码但省略 `data`，工具报 `ZLM listener data unavailable`。公开记录仅保留响应结构，不保存 API cookie。
- 两者使报告等待满 30 秒仍无法确认清理；独立辅助查询显示资源确实为零。此处是监控适配问题，不是已证实的资源泄漏。
- 需按实际 API 契约增加结构兼容与回归测试，不能简单把所有未知响应都视为空。

## 阶段 4：跨循环持续观看取证

```bash
python3 tools/gb28181-load-test/reports/retest-20261011/probe.py tcp-loop --index 3 --mode TCP-PASSIVE --duration 65 --hold 120 --watch --decode-seconds 40 --debug-ts
```

使用身份 `37020000001110603001`，仍然只点播一路。FFmpeg 请求 40 秒输出并保存输入/解码时间戳摘要，用于观察跨越现有 PS 文件的 30 秒周期；若出现时间轴异常，不把解码退出码或 WVP 成功响应视为质量验收通过。

实际结果（11:17:27–11:19:03）：

- 点播 1/1 成功，媒体保持约 44 秒，覆盖至少一个 30 秒输入文件周期；60 秒 REGISTER 续订也得到成功响应。
- 实际 RTP 1202 包、1266464 字节，发送错误 0。结束时设备主动 BYE 1/1 成功，最终媒体/listener/API 可见 SIP 会话均为 0。
- FFmpeg 解码 1097 帧，但输出进度始终停留在 `00:00:00.640000`，没有达到请求的 40 秒。发送结束后进程退出码仍为 0，不能用于判断连续播放通过。
- `-debug_ts` 显示 RTSP 解复用输入的 PTS/DTS 大量重复，例如 `pkt_pts:-45000`、`pkt_dts:-45000`，解码后的 `frame_pts:3600` 大量重复。异常在第一次循环结束前已经出现，不仅是跨文件循环边界才出现。
- 已将定位范围缩小到媒体发送/ZLM 解析及 RTSP 输出时间轴链路；本轮没有修改工具或 ZLM 来绕过问题，也不以本机 FFmpeg 的退出码冒充修复证据。
