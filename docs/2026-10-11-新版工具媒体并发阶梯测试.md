1. TCP 10 路，80 秒，2 次点播/秒，每轮持有 25 秒。
2. TCP 25 路，90 秒，5 次点播/秒，每轮持有 30 秒。
3. TCP 50 路，100 秒，10 次点播/秒，每轮持有 35 秒。

仅前一档无业务异常、有效资源残留为零、磁盘/主机资源满足保护条件时推进。每路 HTTP-FLV 观看连接持续消费视频，避免无人观看自动关闭干扰持续收流；首台和末台另用 FFmpeg 验证解码时间推进。最后一档目标读取 40 秒，覆盖 30 秒素材循环。

保护条件：磁盘剩余低于 4 GiB、可用内存低于 1 GiB、主机 CPU 连续三个 2 秒采样 busy 超过 85%、点播/停止/RTP 发送错误、观看连接异常或阶段超期，均中断本次工具并暂停升级。只清理本次工具自身会话，保留服务与历史数据。

### 1. 10 路重复点播和停止

执行时间：2026-10-11 11:43:02—11:44:53（北京时间）。

```bash
cd /data/shizy/wvp-GB28181-pro/tools/gb28181-load-test
LC_ALL=C python3 reports/media-stair-20261011/probe.py tcp-10 \
  --index 1 --count 10 --duration 80 --hold 25 --rate 2 --start-rate 5
```

步骤：检查空闲媒体基线和未占用编号段 → 注册 10 台模拟设备 → 确认在线及目录入库 → 为本轮设备设置 TCP-PASSIVE → 每秒发起 2 次点播 → 持续消费 HTTP-FLV → 对首台和末台进行 5 秒 RTSP 解码 → 按 25 秒持有期停止并再次点播 → 工具退出发送 BYE → 检查 30 秒资源清理窗口。

注册、在线设备和入库通道均 10/10；点播与媒体确认 30/30；HTTP 停止 20/20；设备主动 BYE 发送及 200 响应 10/10。峰值为 10 条业务流、10 条 SIP 会话、10 个 listener、10 个观看连接。首末台各解码 131 帧，媒体时间 5 秒、错误日志为空。RTP 发送 16,729 包、16,011,095 字节，无发送错误；观看端消费 14,857,068 字节，无连接错误。

| 37020000001110702010 | 178 | 0200004332 | e6716a6983ab7ba764f1d600c3fbeccc@192.168.7.9 |

脱敏抓包文件：`tools/gb28181-load-test/reports/retest-20261011/media-stair-tcp10-bye-repro.wire.jsonl`。使用 `packetTime` 判断网络时序，`at` 受抓包文本缓冲影响，不作为精确发送时间。两条残留对应的 BYE/200 如下：

| 设备末尾 | BYE 到达 | 200 返回 | CSeq |

### 3. 平台主动停止对照

为区分设备退出与平台主动停止的清理路径，保持同样 10 路，不升级负载。使用第三组全新编号，持续播放并完成跨循环解码后，第 65 秒通过 WVP API 逐个停止本轮点播；模拟设备继续运行至第 85 秒，期间能够响应平台 BYE。

同时执行：

```bash

```

执行时间：11:52:32—11:53:58。注册、在线、目录、点播及媒体确认均 10/10；首末台各解码 1,006 帧、40 秒，跨素材循环且错误日志为空。RTP 发送 12,938 包、12,365,261 字节，无发送错误；HTTP-FLV 消费 11,575,187 字节，无观看连接错误。

本轮额外停止由诊断脚本发起，单独记入 `.probe.json` 的 `manualStops`，不冒充工具自身的停止计数。10 次 API 停止均成功，返回时间为 11:53:38.224166—11:53:38.436813。抓包记录 10 个平台 BYE 和全部对应的设备 200 响应。11:53:40.476847 首次采到媒体流、SIP 会话及 listener 均为零，此时 10 台模拟设备仍在线；之后保持零残留直至退出。2 秒采样只能说明该时间点之前已归零，不能给出精确的实际清理耗时。

工具退出时的清理检查约 1.013 秒完成，无超时、无残留。此值是退出后的检查时长，不是前述主动 API 停止的清理延迟。因为停止由脚本发起，工具内的停止成功率仍显示 N/A；监控数据也不完整，容量判定为 `INCONCLUSIVE`，不是完整容量验收通过。

对照结果支持把排查重点放在设备集中退出的时序及平台清理路径上，但本轮主动停止是顺序调用，前两轮设备退出是并发动作，存在并发程度等差异，不能仅凭此对照证明某一个具体竞态。

### 资源采样与判定边界

| 项目 | 重复启停 | 集中退出 | API 停止对照 |
|---|---|---|---|
| 主机 CPU busy 平均 / 峰值 | 9.65% / 14% | 9.25% / 13% | 9.77% / 19% |
| WVP 进程 CPU 平均 / 峰值 | 14.49% / 56% | 9.77% / 48.5% | 11.86% / 67.16% |
| WVP RSS 峰值 | 778.23 MiB | 793.61 MiB | 805.49 MiB |
| ZLM RSS 峰值 | 32.48 MiB | 33.97 MiB | 33.87 MiB |
| 工具 RSS 峰值 | 12.70 MiB | 12.70 MiB | 12.51 MiB |
| Young GC / Full GC | 2 / 0 | 2 / 0 | 2 / 0 |
| 累计 GC 时间增量 | 0.057 秒 | 0.028 秒 | 0.048 秒 |
| 磁盘最低可用量 | 13.212 GiB | 13.188 GiB | 13.171 GiB |

进程 CPU 使用 `pidstat` 口径，100% 代表占用一个逻辑 CPU，而不是整机 16 个逻辑 CPU 的全部容量。GC 占用百分比针对当前已提交的区域，不能直接解释为最大堆用尽。现有资源没有达到停止阈值，阻止升级的是生命周期清理异常，不是 CPU、内存或磁盘极限。

工具报告 `zlm.peakStreams=50` 是多协议媒体条目数；本轮实际业务流峰值为 10，不能解读为 50 路摄像头。缺少 Prometheus 资源采样时，即使报告中的 `resourceSloPassed=true`，也不能视为资源监控完整，必须结合 `monitoringComplete=false` 和缺项阅读。存在明确清理失败时总 verdict 为 `FAIL`；只有没有业务失败但监控仍不完整时，才应保留容量结论 `INCONCLUSIVE`。
