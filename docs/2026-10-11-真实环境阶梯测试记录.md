## 已确认的问题

### P1：媒体发送速率与真实摄像头不相符，阻断媒体容量测量

- 源码：`tools/gb28181-load-test/internal/rtp/source.go:18`，`SharedReader.Next()` 每轮复制并返回整个文件，而不是按视频访问单元读取；下一轮又重置 RTP 时间戳。
- 发送器：`tools/gb28181-load-test/internal/rtp/tcp_sender.go:17`，每轮结束后默认等待 40 ms。
- 现场：单路 RTSP 媒体输出 `bytesSpeed` 约 14.57–15.22 MB/s，即约 116–122 Mbps；ts 条目约 23.30–25.00 MB/s。各协议的 bytesSpeed 不是独立摄像头路数，也不是可以简单相加的 RTP 入站码率。
- 约 10 秒内磁盘可用空间从 1860.04 MiB 降到 1482.21 MiB，下降约 377.83 MiB（396 MB）。录像和其他媒体输出落盘都会贡献磁盘变化，不能将全部变化都归因于 MP4。
- 修复方向：按 PS/PES 和视频访问单元解析，按 PTS/DTS 或明确的目标帧率/码率调度；循环播放时保证 RTP 时间戳持续推进，并暴露实际发送速率、包数和错误。

### P1：模拟设备 INVITE 响应 CSeq 固定为 1

- 源码：`tools/gb28181-load-test/internal/device/device.go:348`。
- 信令证据：09:24:37 WVP 发出 `CSeq: 319 INVITE`，工具返回 `CSeq: 1 INVITE`，随后观察到 `CSeq: 1 ACK`。
- 影响：响应与原请求序号不匹配，无法将本轮结果视为标准 SIP Dialog 的可靠建立与清理验证。
- 修复方向：响应必须回显原请求 CSeq，并正确保存 Dialog 的本地/远端 URI、tag、Contact/路由信息。

### P1：模拟设备 BYE 格式错误，真实 WVP 返回 400

- 源码：`tools/gb28181-load-test/internal/device/device.go:322` 将整个 From 头保存为请求目标，`tools/gb28181-load-test/internal/sip/message.go:70` 又对头值进行尖括号包装。
- 信令证据：09:24:52 发出 `BYE <sip:37020000002000000001@3702000000>;tag=... SIP/2.0`，WVP 在约 2 ms 后返回 `400 Bad Request`。
- 工具报告的 `deviceByeSent=1` 只表明发送了报文，不能证明 BYE 被接受或 SIP 会话正常清理。
- 修复方向：区分 Request-URI 与 From/To 头，保存完整 Dialog 状态，正确构造 BYE，并等待、统计 BYE 的最终响应和超时结果。

### P2：报告成功率统计存在实测误判

- 源码：`tools/gb28181-load-test/internal/runner/runner.go:355`。
- 正常 Digest 注册经历无认证请求及带认证请求，报告用 1 次成功除以 2 次请求，因此 10/50/100 台全部注册成功的三档均被显示为 50%。
- DeviceInfo/DeviceStatus 被混入 Catalog 计数，单路显示 Catalog 成功率 200%，10 台显示 180%。
- 分母为 0 时直接返回 1，三档从未执行点播、媒体或停止，却报告这些成功率为 100%；续订专项没有新 Catalog，也可能报告目录为 0%，尽管已有通道均存在。
- 修复方向：区分设备级成功、请求/挑战事件、实际执行项目和不适用项目；按命令类型单独统计目录；没有执行的项目输出 N/A，而非 100%。

### P2：结束时残留流检查缺少收敛等待

- 单路中断后的工具即时报告为 `residualStreams=1`，约 5 秒后的外部采样已没有该业务流。
- 工具立即进行最终快照，不等待 SIP/Hook/ZLM 清理收敛，也不扣除非测试流基线；容易把短暂清理延迟判成永久残留。
- 修复方向：按测试编号范围过滤，设置明确的清理宽限期，轮询业务流、listener 和会话直到归零或超时，再给出残留判定。

### P2：仅启用 ZLM 监控时仍强制要求 Prometheus URL

- 首次预备执行 `single-hold` 仅配置 ZLM 采样，工具立即退出：`monitoring.prometheus.url must be a valid http(s) URL`，没有实际启动设备。
- 源码：`tools/gb28181-load-test/internal/config/config.go:435`。
- 后续配置填写本机 9090 作为明确不可用的监控地址，保留 ZLM 实测采样和监控缺失信息；没有将缺失值当作资源空闲证据。
- 修复方向：监控源分别可选；ZLM-only 模式可以运行，但报告应清楚标记资源容量判定不完整。

## 环境限制与待确认现象

- 磁盘 99% 且开启录像：禁止继续高并发媒体加压；先由用户安排磁盘空间/测试录像策略。
- 没有可访问的本机 Prometheus，WVP actuator health 为 404：无法完整评估 JVM、线程池、Redis/MySQL 延迟和资源瓶颈。需要部署或提供实际监控地址并校准查询标签。
- 无人观看自动关闭开启，ZLM `general.streamNoneReaderDelayMS=20000`：本次单路约 10 秒媒体存活后即被安全中止，因此并未实测该 20 秒自动关闭流程。持续媒体阶梯需明确观看端或隔离测试环境策略。
- 运行 WVP 构建与当前仓库不同：不能把现场结论当作当前 HEAD 全部代码的验收。
- 有媒体时 `/api/play/ssrc` 仍返回 0；模拟器 CSeq/Dialog 不正确可能影响会话保存，不能据此直接归责 WVP。需修复模拟器协议后结合服务日志及 Redis 索引复测。
- 心跳获得 SIP 200，但心跳时间/历史 API 为空：需进一步检查运行构建、记录配置与实际 Redis 数据，不能直接推断心跳被丢弃。
- 中断后原 listener 消失、另一 SSRC 的 listener 短暂出现，后续归零：可能涉及自动拉流或截图路径，但没有当前服务日志佐证，根因未确认。
- 本轮只通过 WVP 查询接口观察会话，没有直接验证 Redis InviteInfo/SIP V2 主记录和索引，因此不声称 Redis 层完全无残留。
