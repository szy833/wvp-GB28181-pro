# 启动循环依赖与 SSRC 调度生命周期修复

## 1. 故障与根因

2026-10-11 部署统一 Invite 生命周期版本后，Spring 容器初始化失败。

首个异常的依赖环路为：

```text
RedisAlarmMsgListener
  -> DeviceServiceImpl
  -> CatalogResponseMessageHandler
  -> ResponseMessageHandler（继承的 platformService）
  -> PlatformServiceImpl
  -> PlayServiceImpl
  -> DeviceServiceImpl
```

统一广播清理时，`PlatformServiceImpl` 新增了直接注入的 `IPlayService`，闭合了该环路。
`DeviceServiceImpl` 自己的 `playService` 已有 `@Lazy`，但这不能切断经由平台服务形成的另一条依赖链。

随后 `ssrc-rebuild` 每 5 秒报告 RedisProperties 配置绑定异常，是另一个生命周期缺陷引出的连带报错：

- `SSRCFactory.init()` 在 `@PostConstruct` 中启动后台任务，此时整个容器未必已完成刷新。
- 原实现没有销毁钩子，其他 Bean 创建失败后，已启动的调度任务仍然运行。
- 后台查询媒体节点时触发依赖初始化，最终遇到 `ApplicationContext has not been refreshed yet`。

日志不能据此认定 Redis 地址、密码或数据库迁移存在错误；不应以修改 Redis 配置处理本次故障。

## 2. 修改

### 2.1 广播停止服务运行时解析

`PlatformServiceImpl` 注入 `ObjectProvider<IPlayService>`，仅在匹配到本平台广播会话、实际执行 `stopBroadcast()` 时取出停止协调服务。

这消除了 Bean 创建阶段的平台到点播服务的强制初始化依赖，保留运行期统一清理路径：

- 主动停止仍走 `stopIfOwner()`。
- 收到对端 BYE 后仍走 `stopAfterDeviceBye()`。
- 不属于本平台的会话不获取停止服务，也不执行停止。

没有开启 `spring.main.allow-circular-references`，没有恢复旧 Invite 存储或旧清理实现。

### 2.2 SSRC 对账与应用生命周期绑定

- `@PostConstruct` 只初始化国标域片段，不启动任务。
- 收到 `ApplicationReadyEvent` 后启动一次周期对账，立即执行首次检查，后续采用 5 秒 fixed-delay。
- 就绪前的媒体上线事件不启动后台查询；首次周期对账会覆盖已上线节点，就绪后的上线事件仍安排 1 秒后重试。
- 就绪事件重复到达不重复安排周期任务。
- 容器关闭事件及 `@PreDestroy` 均可关闭调度器，关闭操作幂等。
- 启动中途失败时，即使没有发出正常关闭事件，已创建 Bean 的销毁钩子也会关闭调度器。
- 关闭后，迟到的就绪、上线事件以及已取出的尚未执行回调不再发起对账。

`shutdownNow()` 会取消排队任务并中断执行中任务，但不保证强制终止所有不响应中断的第三方网络调用；已有调用仍受客户端连接/读取超时约束。

## 3. 回归范围与证据

之前的生命周期单元测试验证了业务状态机，但没有真实组装这条 Spring 依赖链，这是本次启动缺陷未被拦截的测试缺口。

本次新增：

1. `InviteStartupContextTest`：真实创建报错链路上的 7 个生产 Bean，启用生产 `AsyncConfig`，明确禁止循环依赖；验证正序和倒序注册均可完成容器刷新，并验证 Catalog handler 已完成注册。链路以外依赖使用 mock，不访问真实 SIP、数据库或 Redis。
2. `SSRCFactoryLifecycleTest`：验证初始化不调度、提前上线不调度、就绪仅启动一次、上线重试、关闭后无迟到工作、启动失败关闭调度器。
3. `PlatformInviteActivationTest`：补充广播停止的运行时服务获取、是否发送 BYE 的分流以及平台归属保护。
4. 原 SSRC 上线恢复测试增加应用就绪步骤，继续使用真实调度器验证延迟恢复。

修复前新增 7 项测试全部失败，两个容器测试复现了原循环依赖，生命周期测试复现提前调度和缺少销毁。
修复后针对性回归共 33 项，失败 0、错误 0、原有跳过 1。
全量 Java 回归共 270 项，失败 0、错误 0、原有跳过 1，构建结果为 `BUILD SUCCESS`，
包含隔离 Redis 容器中的生命周期与原子清理集成测试。

隔离构建输出位于 `target/invite-lifecycle-check/maven-build`，不覆盖部署用的根 `target/classes`。

测试日志：

- 修复前：`target/invite-lifecycle-check/maven-startup-red.log`
- 针对性回归：`target/invite-lifecycle-check/maven-startup-green-final.log`
- 全量回归：`target/invite-lifecycle-check/maven-startup-final.log`

## 4. 真实部署待验收项

本次不操作现网数据库、Redis，不启停或部署现网服务，也不重复执行已完成的数据库迁移。
上述隔离容器测试不等于完整生产应用已经启动成功；新部署包仍需验证以下内容：

1. 启动日志出现 `Started VManageBootstrap`，且不再出现 Bean 循环依赖报告。
2. 启动时不再出现 `has not been refreshed yet` 引起的 SSRC 连续异常。
3. 应用就绪后 SSRC 对账成功；首次对账完成前自动分配可能暂时拒绝，这是现有安全准入机制。
4. 分别验证点播、主动停止、设备主动 BYE、无人观看关闭后再次点播，以及平台广播停止。
5. 验证停机或人为制造启动失败后，日志不再每 5 秒输出 SSRC 对账调用。

风险：完整服务启动会执行既有设备/平台状态初始化；点播和广播验收会创建 SIP/RTP 会话。
应在约定测试窗口内执行，测试后检查会话、监听器和通道投影均已清理。
