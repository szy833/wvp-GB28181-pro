# 50 与 100 路继续阶梯压测

## 计划与风险

用户在完整 25 路三轮复验通过后授权继续压测。本轮按 50 → 100 路进行，每级通过且独立终检无残留才升级，不突破 100 路。上轮证据见 [25路复验](2026-10-12-发送错误分类与终态报告修复及25路复验.md)。

- 保持 WVP PID 17835、ZLM PID 13291，不部署、重启、调时、手工清 Redis/SQL 或删除设备，不触碰真实摄像头与 `t.cap`，不暂存或提交 Git。
- 使用 index=40（50 台）和 index=41（100 台）的新编号段，先只读核验无设备/通道、无活动业务及媒体残留。工具使用上轮同一独立候选二进制，SHA256 为 `f20a9577d3254d06ee9d4069bec96ede9d51f8f789c2d4daa067e857940ef208`。
- REGISTER 10 台/秒；点播分别 10 和 20 次/秒，最多 20 个 HTTP worker；TCP-PASSIVE，素材 `sample-v2.ps` 约 0.209 Mbps。
- 每级三轮点播；每轮全路 HTTP-FLV 观看 45 秒，首末两路 RTSP 各解码 40 秒。第一轮重复停止后稳定观察 70 秒；第二轮验证旧流停止不能关闭新代，再观看、重复停止并观察 10 秒；第三轮在带流状态下模拟设备主动 BYE 退出，归零后观察 70 秒。
- 每次清理必须在 70 秒内收敛；之后独立只读三次快照间隔 35 秒，核验 Invite/owner/job/lease/索引、SQL 代次与投影、SIP、RTP listener、ZLM 媒体、SSRC。
- 磁盘低于 4 GiB、可用内存低于 1 GiB、整机 CPU 连续三次 2 秒采样超过 85%，或协议/发送/观看/解码错误、设备离线、清理残留，立即停止本级，禁止升压。失败后仍记录独立清理终态，不能以清理成功覆盖测试失败。

凭据仅在内存中处理，通过 stdin 传给只读数据库探针，不进入 argv 或公开报告。最初尝试读取本仓库本地配置，数据库鉴权拒绝；随后使用用户此前提供的凭据，通过关闭回显的输入复核成功。不修改本地配置，私有模拟器配置权限 0600，生成报告、二进制和现场诊断保留在已排除目录。

现场辅助入口为 `target/invite-lifecycle-check/continue_stairs.py`，复用已有阶梯与独立核验脚本，提供 preflight/run/verify 三种操作；ZLM 退出后另外使用 offline-audit 做不依赖媒体节点的业务终检，媒体计数明确不可用。全部新原始证据使用独立目录，不覆盖历史失败和通过证据。现场脚本依赖此环境的地址/JDBC 探针，保留在 target，不作为通用产品的一键容量基准纳入 Git。

## 步骤

1. 核验服务、端口、磁盘/内存、工具 SHA，执行协议错误保护/注册就绪/独立终态的 13 项 Python 诊断回归。
2. 分别对两个新编号段执行只读 preflight。
3. 执行 50 路完整三轮，采集步骤、资源快照、发送分类、观看及解码、进程 CPU/RSS、主机和 WVP GC。
4. 执行 50 路独立终检；通过后才进入 100 路同样流程，否则停止并定位记录。
5. 整理完整可见的 Markdown/JSON 测试项报告，更新本设计/执行文档和待提交清单，不产生 Git 提交。

## 容量边界

生成器、观看端、WVP 和 ZLM 共用宿主机，还有其他工作负载；素材码率低，单轮观看短，未覆盖高码率长稳态及完整 Prometheus/数据库延迟。阶段 PASS 仅证明本级流程通过，容量极限仍为 INCONCLUSIVE，不据此宣称最大容量。

## 本次发现的问题

### 1. ZLM 进程在集中停止阶段退出（阻断继续压测）

第二轮停止后查询连接被重置，随后查询被拒绝。原 ZLM PID 13291 已消失、19001 不监听；WVP 原 PID 17835、5060/18080 监听与版本接口仍在。14:58:24 复核同样如此。压测未调用 ZLM 重启/停止命令，也未对其发送信号；测试只结束自己的模拟器、观看和采样进程。

目前只能确认媒体进程退出，不能在没有退出码、信号、ZLM stderr 或 core 的情况下直接断言 native 崩溃、OOM 或达到容量极限。最后播放快照及主机采样未达到 CPU/内存/磁盘保护线，但这不能排除进程内资源、断言或其他外部终止原因。用户限制只操作本仓库，仓库内没有找到此次 ZLM 退出/崩溃证据，未读取仓库外系统/部署日志。

后续用户指定 `zlm` 会话及 `/data/shizy/GB28181/mediaServer` 的 core，授权只读取证。终端与 GDB 均确认 14:48:22 的 SIGSEGV；core 中正查询该残留流的 TS 媒体对象，`MediaSource::isRecording()` 对空 muxer 调用 `isRecording(type_mp4)`，访问 `0x2b0` 崩溃。这将原因从“进程退出待确认”推进为已证实的 ZLM 空指针缺陷；前段记录仍保留为当时的证据边界。详情、二进制身份、反汇编与后续验证方案见 [ZLM core 分析](2026-10-12-ZLM集中停流崩溃core分析.md)。没有修复、重启或继续压测，100 路 FAIL 与容量 INCONCLUSIVE 不变。

用户随后指定 `/data/shizy/ZLMediaKit` 源码并授权代理联网检索。源码/core 进一步确认：外层 TS 事件代理仍存在，内层总 muxer 的 weak delegate 已过期，旧版基类 getMuxer 返回 nullptr。GitHub PR #4775 已于 2026-07-13 合并，提交 `fcdd7bd` 改为获取失败抛异常；当前部署 `5f11d3b` 不含该修复。截至检索的上游 master 保留修复，已核对真实 diff，不把 PR 初始“逐处判空”描述当作合并补丁。完整根因和修复边界已追加到上述分析文档；本地仍未修改/编译/部署，需新包真实复验才能认定现场已修复。

### 2. ZLM 失联后 RTP 清理无法确认，留下一个旧代待办

残留设备 `37020000001110741099`，通道数据库 ID 682，第二代 Invite `1dc73627-741d-450c-a97b-2e22afe74310`；流 `gb_1dc73627741d450ca97b2e22afe74310`，原接收端口 41476，SSRC `0200003656`。

BYE=1、SIP=1、STATE=1，但 RTP 未完成；`byeAcknowledged=true`，SQL 通道 CLOSED、stream=null，SIP 会话/删除待办为 0。ACTIVE、PENDING、SSRC 预留、该设备索引各为 1，PLAYING 为 0。三次独立快照和 14:58:24 再次审计均确认残留，不是观察窗口暂时未到。

代码对应 `PlayServiceImpl.processInviteCleanup()` 的 RTP 分支（约 1829 行）及 `closeInviteRtp()`（约 1993 行）：关闭调用后，必须使用 `listRtpServer()` 和 `probeStream()` 确认原代消失，才完成 RTP 步骤并释放 lease。ZLM 完全不可查询时不能满足该条件，任务保留并重试。这是**媒体节点失联后的关闭确认未闭环**，不是此前的 BYE 终止超时，也不是 InviteInfo 删除 CAS 重试耗尽。不能手工删除主记录、待办或 SSRC 制造归零；后续需设计节点代次/关闭确认方案并在新授权下实现与复验。

### 3. 在线列表与实际失联存在分钟级延迟

14:51:56、14:52:31、14:53:07 的独立审计中，19001 已不可达，但 `/media_server/online/list` 仍返回该节点。后续只读查询确认缓存 status=false、在线负载 ZSET 已移除该节点，14:58:24 保持离线。配置中的 hookAliveInterval=10 秒，源码预期两次未收到心跳后探测；实际传播延迟显著更长。
