# 大规模设备目录树改造设计

**设计日期：** 2026-08-02  
**设计状态：** 待实现  
**适用范围：** 行政区划树、业务分组树、设备目录树及其前端懒加载

## 1. 背景与问题

当前项目已经提供多组分页接口：

- `/api/device/query/devices/{deviceId}/channels`：分页查询设备通道。
- `/api/device/query/sub_channels/{deviceId}/{channelId}/channels`：分页查询子目录通道。
- `/api/common/channel/list`：全局通道分页查询。
- `/api/common/channel/civilcode/list`：行政区划通道分页查询。
- `/api/common/channel/parent/list`：业务分组通道分页查询。

但目录树使用的接口仍然是无分页返回：

- `src/main/java/com/genersoft/iot/vmp/gb28181/controller/RegionController.java` 的 `/api/region/tree/list`。
- `src/main/java/com/genersoft/iot/vmp/gb28181/controller/GroupController.java` 的 `/api/group/tree/list`。

当 `hasChannel=true` 时，后端会一次性查询父节点下的全部通道。前端 `RegionTree.vue` 和 `GroupTree.vue` 虽然只显示前 50 条，但会先接收并保存完整响应，再通过 `nextData` 在浏览器端切分。

几十万通道时会产生以下问题：

1. 数据库执行全量查询，可能扫描大量记录。
2. HTTP 响应体过大，增加网络和 JSON 序列化开销。
3. 浏览器需要一次性解析和保存全部节点，内存占用随总数据量增长。
4. 区域节点和通道节点混合查询，分页和排序边界不清晰。
5. `DeviceTree.vue` 的 `device` 属性没有用于限制目录范围，设备目录和全局资源树边界不明确。
6. 通道 SQL 使用 `COALESCE(gb_civil_code, civil_code)`、`COALESCE(gb_parent_id, parent_id)`，大表下索引利用率不稳定。

## 2. 设计目标与非目标

### 2.1 设计目标

- 后端单次最多返回固定数量节点，默认 50，最大 200。
- 使用游标分页，避免高页码 `OFFSET` 的性能衰减。
- 区域、分组、通道分别分页，前端只保存已经展示的节点。
- 支持全局资源树和单设备目录树两种查询范围。
- 保留旧接口，允许前端和第三方调用方分阶段迁移。
- 对非法范围、游标、页大小和父节点进行校验。
- 提供查询耗时、返回数量、游标失效和旧接口使用情况的观测能力。

### 2.2 非目标

- 第一阶段不构建全量目录快照。
- 第一阶段不改变设备目录同步协议和数据库主表的数据语义。
- 第一阶段不要求分页期间的强一致快照；目录变更采用可接受的弱一致性游标。

## 3. 方案选择

### 3.1 直接改造现有树接口

给 `/api/region/tree/list` 和 `/api/group/tree/list` 增加分页参数。实现简单，但会改变现有 `List` 返回类型，且区域节点和通道节点混合分页，兼容性和查询边界较差。

### 3.2 新增统一目录树子节点接口（推荐）

增加统一的游标分页接口，按父节点类型和子节点类型查询一页数据。区域、分组和通道使用独立查询，保留现有接口作为兼容入口。

优点：

- 不需要一次性构造完整树。
- 可以复用现有设备通道分页服务。
- 使用游标后不受高页码影响。
- 前后端可以逐节点、逐类别迁移。

### 3.3 目录快照

通过后台任务构建版本化目录快照，再按快照分页读取。该方案适合更高规模和强一致读取，但需要新增快照表、版本切换和重建任务，第一阶段暂不采用。

## 4. 总体架构

采用“统一目录树子节点接口 + 类型独立分页 + 前端节点级加载”的架构：

```text
前端目录树
    -> 统一目录树子节点接口
    -> 目录树查询服务
       -> 区域查询
       -> 分组查询
       -> 设备通道查询
       -> 行政区划通道查询
       -> 业务分组通道查询
    -> 数据库游标分页查询
```

方案中的业务模块使用中文名称：

- **目录树子节点查询**：负责统一请求参数、游标和响应模型。
- **目录范围校验**：负责全局范围、设备范围和父节点归属校验。
- **区域子节点查询**：查询行政区划的下级区域。
- **分组子节点查询**：查询业务分组或虚拟组织的下级分组。
- **通道子节点查询**：查询区域、分组或设备下的一页通道。
- **节点分页状态**：前端保存每个树节点各类别的游标和加载状态。

代码类名和方法名继续遵循现有 Java/Vue 命名规范，不使用中文标识符。

## 5. 后端接口设计

### 5.1 统一接口

新增：

```text
GET /api/catalog/tree/children
```

请求参数：

| 参数 | 说明 | 默认值 |
|---|---|---|
| `scope` | 查询范围：`GLOBAL` 或 `DEVICE` | `GLOBAL` |
| `deviceId` | 设备编号，设备范围时必填 | 空 |
| `parentType` | 父节点类型：`ROOT`、`REGION`、`GROUP`、`CHANNEL` | `ROOT` |
| `parentId` | 父节点编号，根节点为空 | 空 |
| `childType` | 子节点类型：`REGION`、`GROUP`、`CHANNEL` | 必填 |
| `query` | 名称或编号查询条件 | 空 |
| `pageSize` | 单页数量 | 50 |
| `cursor` | 游标 | 空 |

响应结构：

```json
{
  "list": [
    {
      "treeId": "region-110000",
      "nodeType": "REGION",
      "deviceId": "110000",
      "name": "北京市",
      "status": "ON",
      "hasChildren": true
    }
  ],
  "nextCursor": "...",
  "hasMore": true,
  "pageSize": 50
}
```

约束：

- `pageSize` 必须在 1 到 200 之间，超出范围直接返回参数错误，避免调用方无意触发大页查询。
- 游标必须绑定范围、父节点、子节点类型和查询条件，禁止跨节点复用。
- 游标有效期默认 5 分钟。
- 默认不返回精确 `childCount`，避免展开节点时执行昂贵的 `COUNT(*)`。
- 父节点不存在时返回空页，不执行全局扫描。

### 5.2 类型查询

区域查询：

```text
parentType=ROOT|REGION
childType=REGION
```

分组查询：

```text
parentType=ROOT|GROUP
childType=GROUP
```

通道查询：

```text
parentType=REGION|GROUP|CHANNEL
childType=CHANNEL
```

设备目录查询使用：

```text
scope=DEVICE
deviceId=设备编号
parentType=ROOT|CHANNEL
childType=CHANNEL
```

设备通道和子目录优先复用现有 `queryChannelsByDeviceId`、`getSubChannels` 等分页服务；区域和分组通道增加对应的分页查询方法，不再调用当前返回全量列表的 Mapper 方法。

### 5.3 区域和通道分开分页

一个父节点展开时，组织节点和通道节点使用独立请求和独立游标：

```text
查询区域/分组子节点
查询通道子节点
```

这样避免跨表 `UNION`、混合排序和共享游标带来的复杂性。前端可以按“组织节点在前、通道节点在后”合并展示，但两类数据的加载状态保持独立。

## 6. 数据库查询设计

### 6.1 游标分页

不使用高页码 `OFFSET`，使用稳定排序键进行键集分页：

```sql
WHERE id > #{lastId}
ORDER BY id ASC
LIMIT #{pageSize}
```

如果按名称排序，游标包含名称和主键：

```sql
WHERE name > #{lastName}
   OR (name = #{lastName} AND id > #{lastId})
ORDER BY name ASC, id ASC
LIMIT #{pageSize}
```

游标至少包含父节点、子节点类型、最后排序键和查询条件摘要，避免请求参数变化后继续使用旧游标。

### 6.2 索引和有效字段

第一阶段增加并验证以下组合索引：

```text
(gb_civil_code, id)
(civil_code, id)
(gb_parent_id, id)
(parent_id, id)
```

将 `COALESCE` 条件改写为可利用索引的等值或空值分支，并针对项目支持的数据库执行 `EXPLAIN`。

如果数据规模继续扩大，再增加由目录同步和修改逻辑统一维护的规范化字段：

```text
tree_civil_code
tree_parent_id
```

后续直接按规范化字段查询，避免函数表达式和 `OR` 条件导致索引不稳定。

### 6.3 子节点标识

每个节点返回：

```text
treeId
nodeType
deviceId
name
isLeaf
hasChildren
```

`hasChildren` 不允许逐条查询。可采用页面结果批量查询子节点存在性，或在 SQL 中使用批量 `EXISTS`；数据库压力较大时可暂时只返回可展开标识，在实际展开时再确认。

## 7. 前端改造设计

改造范围：

- `web/src/views/common/RegionTree.vue`
- `web/src/views/common/GroupTree.vue`
- `web/src/views/common/DeviceTree.vue`
- `web/src/api/region.js`
- `web/src/api/group.js`

### 7.1 删除全量缓存

移除 `nextData` 及其相关的前端切片逻辑。后端未返回的数据不在浏览器端缓存，点击“加载更多”时重新请求后端。

### 7.2 节点分页状态

每个父节点保存独立状态：

```javascript
{
  loading: false,
  regionCursor: null,
  channelCursor: null,
  hasMoreRegion: true,
  hasMoreChannel: true
}
```

展开节点时加载第一页，加载更多时携带对应类别的游标。没有更多数据时移除加载入口。

### 7.3 搜索和请求竞态

- 搜索结果继续使用现有分页搜索接口。
- 搜索关键字变化时清空旧结果和游标。
- 同一节点同一类别只允许一个请求同时执行。
- 旧请求返回时校验父节点、查询条件和请求序号，过期结果直接丢弃。
- 追加节点前按 `treeId` 去重。

### 7.4 设备范围

`DeviceTree.vue` 需要真正使用 `device` 属性：

- 全局资源树使用 `scope=GLOBAL`。
- 单设备目录使用 `scope=DEVICE&deviceId=...`。
- `onlyCatalog=true` 时只加载设备目录，不加载全局区域和分组资源。

## 8. 兼容策略

保留旧接口：

```text
/api/region/tree/list
/api/group/tree/list
```

新版前端改用 `/api/catalog/tree/children`。旧接口继续保持原返回格式，但增加保护配置：

```text
catalog.tree.legacy-max-size=1000
```

超过限制时记录告警并返回明确错误，不静默截断，避免调用方误以为目录完整。迁移期间增加旧接口调用次数监控，确认无关键调用方后再考虑废弃。

## 9. 一致性、异常与安全

分页采用弱一致性游标：

- 稳定排序保证单次查询结果可继续翻页。
- 分页期间新增数据可能出现在后续页或下一次展开。
- 删除数据不会阻塞查询。
- 前端按 `treeId` 去重。

如果未来需要严格的一致性版本，再引入目录快照。

异常处理要求：

- 缺少设备编号、父节点类型不匹配时返回参数错误。
- 非法或过期游标返回游标失效错误。
- 查询超时只影响当前节点，不降级为全量查询。
- 父节点归属校验失败时不得返回其他设备或其他范围的数据。
- 日志记录范围、父节点、子节点类型、返回数量和耗时，不记录完整游标内容。

## 10. 测试与验收

### 10.1 后端测试

- 区域、分组和通道查询只返回单页数据。
- 游标连续翻页无重复、无遗漏。
- 设备范围不会返回其他设备通道。
- 非法游标、超大页大小和不存在父节点处理正确。
- 新查询不调用旧的全量 Mapper 方法。
- `EXPLAIN` 验证使用预期索引。

### 10.2 前端测试

- 展开节点只发送当前页请求。
- 加载更多会携带上一次游标。
- 不再创建 `nextData` 全量缓存。
- 搜索旧响应不会覆盖新结果。
- 重复节点不会重复插入。
- 区域/分组节点和通道节点可以分别继续加载。

### 10.3 性能验收

至少使用以下规模进行验证：

```text
区域节点：10 万
分组节点：10 万
通道节点：50 万
单父节点通道：10 万
```

验收指标：

- 单次接口最多返回 200 条。
- 索引命中时接口 P95 目标小于 300 ms。
- 单次响应体目标小于 200 KB。
- 前端内存不随未展示数据总量线性增长。
- 不出现无条件全量通道扫描。

## 11. 实施阶段

### 第一阶段：后端分页能力

新增统一接口、响应 DTO、游标编码、范围校验和区域/分组/通道分页查询，保留旧接口。

### 第二阶段：前端树组件迁移

迁移区域树、分组树和设备树，删除 `nextData`，增加节点级游标和加载状态。

### 第三阶段：兼容与观测

增加旧接口告警、查询耗时和游标失败指标，使用大数据量进行压测并根据执行计划调整索引。

### 第四阶段：可选目录快照

仅当游标查询无法满足吞吐量，或业务需要严格目录版本一致性时，再设计目录快照表和版本切换机制。

## 12. 结论

本设计采用：

```text
统一目录树子节点接口
+ 游标分页
+ 区域/分组/通道分类型查询
+ 前端节点级按需加载
+ 复用现有设备通道分页能力
+ 旧接口兼容保留
```

该方案可以消除当前“后端全量查询、前端截取 50 条”的主要性能问题，并为后续目录快照化保留扩展空间。
