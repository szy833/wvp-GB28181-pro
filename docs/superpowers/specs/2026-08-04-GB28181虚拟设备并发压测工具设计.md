# GB28181 虚拟设备并发压测工具设计

## 1. 背景与目标

当前项目缺少大量真实摄像头，无法直接验证 REGISTER、Keepalive、INVITE、RTP 收流、BYE 清理和 ZLMediaKit Hook 在高并发下的表现。本项目在 `tools/gb28181-load-test/` 下建立一个独立的 Go 压测工具，不修改 WVP 生产代码，用虚拟设备替代真实摄像头。

第一版目标：

- 单台压测机支持 1,000 个虚拟设备，架构上预留扩展到 5,000～10,000 个设备。
- 支持 REGISTER、REGISTER 续订、Keepalive、INVITE、200 OK、ACK、BYE 基础流程。
- 支持 UDP RTP/PS 媒体发送；TCP-PASSIVE 作为第二阶段能力。
- 一个预编码视频文件可以被多个虚拟设备复用，但每个设备使用独立设备 ID、通道 ID、Call-ID、SSRC 和 RTP 会话。
- 支持播放成功、无媒体超时、设备主动 BYE、播放停止和重复点播等场景。
- 输出实时 Prometheus 指标，并生成 JSON/CSV 汇总结果。

第一版不实现真实摄像头全部厂商差异、不模拟完整设备配置能力、不进行视频转码性能基准，也不把压测工具作为 WVP 运行时依赖。

## 2. 运行边界

项目目录固定为：

```text
tools/gb28181-load-test/
```

它是独立 Go 模块，可以在仓库根目录之外复制后单独构建，但本次实现文件只放在上述目录以及本设计文档中。

建议压测环境：

```text
压测机运行虚拟设备工具
        │ SIP UDP/TCP
        ▼
WVP GB28181 SIP 服务
        │ Redis / MySQL
        │ HTTP Hook
        ▼
ZLMediaKit
        ▲
        └── RTP/PS 媒体
```

WVP、Redis、MySQL、ZLM 必须使用独立测试实例，不能连接生产数据。设备 ID、SIP ID 和测试流名称统一使用可配置前缀，例如 `loadtest-`，便于清理。

## 3. 技术选型

### 3.1 主程序

- Go 1.22 或更高版本。
- 使用 goroutine 管理虚拟设备，避免“一设备一 OS 线程”。
- 使用标准库 `net`、`context`、`encoding/xml`、`encoding/json`、`flag`。
- SIP 报文采用显式消息构造和解析，设备状态机与网络传输解耦。
- RTP/PS 打包器使用独立接口，便于替换成文件回放、空媒体和实时生成器。

### 3.2 外部工具定位

- SIPp：可作为单独的 SIP 信令基准工具，不作为本项目运行时依赖。
- FFmpeg：用于将样例视频预编码为固定格式；不直接承担 GB28181 SIP 会话。
- GStreamer：后续可作为替代媒体源，但第一版不强制依赖。
- Prometheus/Grafana：采集和展示指标，不影响压测结果采集。

### 3.3 为什么不直接启动大量 FFmpeg

每个设备启动一个 FFmpeg 会把 CPU 和进程调度开销混入 WVP 并发指标。第一版先读取一份预编码媒体文件并复用数据，只为每路 RTP 替换 SSRC、时间戳和目标地址。这样可以优先测量 SIP、WVP、Redis、ZLM 和网络能力。需要测转码能力时，再增加独立的 FFmpeg 多进程模式。

## 5. 虚拟设备状态机

单个虚拟设备状态：

```text
CREATED
  -> REGISTERING
  -> ONLINE
  -> INVITING
  -> SIP_ESTABLISHED
  -> MEDIA_SENDING
  -> PLAYING
  -> STOPPING
  -> OFFLINE
```

异常状态统一进入 `FAILED`，记录错误分类后执行清理。

### 5.1 REGISTER

- 使用独立设备 ID、SIP 用户名、Contact 和 Call-ID。
- 支持无认证和 Digest 认证配置；默认使用无认证，先验证并发链路。
- REGISTER 成功后保存 WVP 返回的 Expires 和本地注册时间。
- 在 Expires 的 1/2 到 2/3 时间点发送续订 REGISTER。

### 5.2 Keepalive

- 按设备配置的周期发送 XML Keepalive。
- 支持固定周期和随机抖动，避免所有设备在同一毫秒发送。
- 统计发送、响应、超时和重试数量。

### 5.3 INVITE

- 设备收到 WVP INVITE 后解析 `m=`、`c=`、`a=setup` 和 `y=`。
- 生成 200 OK，携带可配置的媒体能力和 SSRC。
- 200 OK 后等待 ACK；ACK 超时进入失败清理。
- UDP 模式直接向 SDP 中的 WVP/ZLM RTP 地址发送媒体。
- TCP-PASSIVE 模式第二阶段实现，按 WVP SDP 建立 TCP 连接并发送 RTP。

### 5.4 BYE

支持三种结束方式：

- 压测控制器主动停止；
- 播放持续时间到期；
- 模拟设备在无媒体、网络错误或随机故障时主动发送 BYE。

BYE 发送后等待 200 OK，超时仍关闭本地 RTP 发送器并记录清理异常。

## 6. SIP 和 SDP 设计

### 6.1 标识规则

```text
deviceId = <prefix><序号，固定宽度>
channelId = <deviceId>01
callId = <runId>-<deviceIndex>-<随机串>
stream = <deviceId>_<channelId>
ssrc = <类型前缀><域号><四位序号>
```

所有标识在一次测试运行内唯一，测试结束后可以通过 `runId` 清理。

### 6.2 SDP

UDP 基线 SDP 使用：

```text
v=0
o=<deviceId> 0 0 IN IP4 <deviceIp>
s=Play
c=IN IP4 <wvpOrZlmIp>
t=0 0
m=video <port> RTP/AVP 96 97 98 99
a=recvonly
a=rtpmap:96 PS/90000
a=rtpmap:98 H264/90000
a=rtpmap:97 MPEG4/90000
a=rtpmap:99 H265/90000
y=<ssrc>
```

TCP 模式严格根据 WVP 返回的 `a=setup` 和端口执行，不在模拟器中硬编码连接方向。

## 7. RTP/PS 媒体源

### 7.1 文件预处理

`prepare-media.sh` 使用 FFmpeg 将输入文件转换为固定、可循环读取的 PS 媒体样本。预处理结果保存到压测项目的媒体目录，不提交大视频文件。

推荐固定：

- H.264；
- 25fps；
- 720p；
- 无音频或固定 G.711 音频；
- 固定码率，便于估算网络带宽。

### 7.2 PS over RTP

RTP 发送器负责：

- 生成 RTP 版本、Payload Type、序号和时间戳；
- 将 PS 数据按 MTU 分片，默认不超过 1,400 字节；
- 每个设备使用独立 SSRC；
- 按媒体时间戳控制发送速率；
- 支持实时速度、2 倍速和尽快发送三种模式；
- 统计发送字节、包数、丢弃数和发送耗时。

第一版只支持 UDP 发送。若输入文件无法直接得到可用 PS 单元，工具必须明确报错，不能静默把 MPEG-TS 当作 GB28181 PS 发送。

## 8. 压测场景

### 8.1 基线场景

- 100 个设备注册；
- 每个设备每 60 秒续订 REGISTER；
- 每 10 个设备同时点播一次；
- 播放 60 秒后发送 BYE；
- 重复 10 轮。

### 8.2 阶梯并发场景

设备数按 10、100、500、1,000 递增，每级稳定 10 分钟。点播并发按设备数的 10%～30% 设置，记录每一级的 P50、P95、P99 和错误率。

### 8.3 高 churn 场景

持续执行点播、播放 10～30 秒、停止、再次点播，重点观察：

- RTP 资源是否残留；
- InviteInfo 是否残留；
- SSRC 是否持续增长；
- ZLM RTP 监听器是否泄漏；
- Redis 临时 key 是否过期。

### 8.4 无媒体超时场景

设备返回 200 OK，但不发送 RTP，验证 WVP 是否在 `play-timeout` 窗口内完成超时、BYE、RTP 和 InviteInfo 清理。

### 8.5 故障场景

- 随机丢弃 REGISTER 200 OK；
- 延迟 Keepalive 响应；
- 200 OK 后不发送 ACK；
- RTP 发送中断；
- 随机设备主动 BYE；
- ZLM HTTP 接口不可用；
- 使用 `tc netem` 注入延迟、丢包和连接失败。

  source: ./media/sample.ps

```text

loadtest validate --config configs/example.yaml

```

## 10. 指标和验收标准

### 10.1 指标

设备和 SIP：

- `devices_created`、`devices_online`、`devices_failed`；
- `sip_register_total`、`sip_register_success_total`、`sip_register_timeout_total`；
- `sip_keepalive_total`、`sip_keepalive_timeout_total`；
- `sip_invite_total`、`sip_invite_200_total`、`sip_invite_timeout_total`；
- `sip_ack_total`、`sip_bye_total`；
- REGISTER、INVITE、首个媒体包和 BYE 的延迟直方图。

媒体和清理：

- `rtp_sessions_created`、`rtp_sessions_media_ready`、`rtp_sessions_timeout`；
- `rtp_packets_sent`、`rtp_bytes_sent`、`rtp_send_errors`；
- `device_media_first_packet_seconds`；
- `device_play_duration_seconds`；
- `cleanup_success_total`、`cleanup_timeout_total`、`cleanup_residual_total`。

### 10.2 验收标准

- 100 个设备基线场景连续运行 10 分钟，REGISTER、Keepalive、INVITE、RTP、BYE 均能完成。
- 1,000 个设备阶梯场景可启动、停止并生成完整报告，工具自身无 goroutine 泄漏。
- 同一设备重复点播和停止后，WVP 的 RTP 资源、InviteInfo、SIP 会话和 ZLM RTP 监听器数量回到基线附近。
- 无媒体超时场景能在配置窗口内完成清理，不产生永久运行的虚拟设备会话。
- 所有失败会话都能在 JSON 报告中按阶段和错误类型分类。
- 工具退出码为 0 仅表示测试流程完成，不表示 WVP 达到某个容量；容量结论必须结合 P99、错误率和外部资源指标。

## 11. 观测与排障

测试时同步保存：

- 压测工具 JSON/CSV 报告；
- WVP 应用日志和 `sip` 日志；
- ZLM 日志；
- Redis `INFO`、`SLOWLOG`、命令统计；
- MySQL 慢查询和连接池指标；
- JVM JFR 或 async-profiler 结果；
- 必要时保存 SIP 抓包和 RTP 抓包。

排障优先按照以下链路判断：

```text
REGISTER 成功
  -> INVITE 发送
  -> 设备 200 OK
  -> ACK
  -> RTP 首包
  -> ZLM register Hook
  -> WVP MediaArrival
  -> RTP SUCCESS
  -> BYE / 资源清理
```

不能只使用 SIP 200 OK 或 `InviteInfo.status=ok` 判断媒体成功，必须确认 RTP 首包和 ZLM/WVP 媒体事件。

## 12. 安全与清理

- 默认只允许向配置中的测试目标发送 SIP/RTP，不接受外部控制命令。
- `runId`、设备前缀和报告目录必须在启动时校验，禁止为空或使用生产前缀。
- 工具退出、信号终止和场景结束时统一发送 BYE，并执行本地会话清理。
- 运行前后记录 WVP、Redis、MySQL、ZLM 的基线数量。
- 禁止使用生产数据库、生产 Redis 和生产 ZLM 进行压测。
- 不修改或提交仓库中的 `t.cap`。

## 13. 已知限制与后续扩展

第一版限制：

- 只保证 UDP 媒体链路；TCP-PASSIVE 需要第二阶段实现。
- 只实现常用 H.264 PS 流，不覆盖所有厂商私有 XML 和 SDP 差异。
- 文件复用模式不代表转码性能。
- 不模拟摄像头图像采集、编码抖动和硬件故障。

后续扩展顺序：

1. TCP-PASSIVE RTP 发送；
2. Digest 认证和设备厂商 XML 模板；
3. 多媒体文件和动态码率；
4. 集群模式，将虚拟设备分布到多台压测机；
5. 结果推送到 Prometheus/Grafana 和自动容量报告。
