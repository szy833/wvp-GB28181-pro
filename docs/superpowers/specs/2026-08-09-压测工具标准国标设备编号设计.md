# 压测工具标准国标设备编号设计

## 背景

当前压测工具默认生成 `loadtest-000001` 形式的设备编号。该编号便于识别测试设备，但不符合 WVP 严格国标编号校验要求：WVP 默认要求 REGISTER 的 From 用户名是 20 位纯数字。因此设备会在 REGISTER 阶段被拒绝，后续 MESSAGE 和 HTTP 点播均无法形成完整的 GB28181 流程。

本次改造让压测工具支持标准 GB28181 编号，同时保留原有带前缀编号作为显式兼容模式，避免现有测试配置立即失效。

## 目标与非目标

### 目标

- 支持生成 20 位纯数字的设备 ID。
- 支持生成 20 位纯数字的通道 ID。
- 设备 ID、通道 ID、SIP Call-ID、流名和 SSRC 在单次运行内保持唯一且可追踪。
- 标准模式无需关闭 WVP 的 `user-settings.device-id-strict` 即可完成 REGISTER。
- 保留 `loadtest-` 编号模式，供非严格 WVP 或兼容旧配置使用。
- 在配置加载阶段校验编号格式、容量和设备/通道冲突，避免运行中才失败。

### 非目标

- 不修改 WVP 设备 ID 校验规则。
- 不自动探测或占用生产环境编号段。
- 不从数据库或 WVP 读取可用设备编号；编号分配完全由压测配置负责。

## 配置设计

新增 `identity` 配置块：

```yaml
identity:
  mode: numeric
  deviceBase: "34020000001110000000"
  channelBase: "34020000001310000000"
```

字段含义：

- `mode`：`numeric` 或 `legacy`。`numeric` 生成标准 20 位数字编号；`legacy` 保留当前 `idPrefix` 行为。
- `deviceBase`：数字模式的设备起始模板，必须是 20 位纯数字。第一个设备使用 `deviceBase + 1` 的序号语义，后续设备递增。
- `channelBase`：数字模式的通道起始模板，必须是 20 位纯数字，和设备按相同索引递增。
- `idPrefix`：仅在 `legacy` 模式使用，继续要求以 `loadtest-` 开头。

为避免把模板最后一位当作普通数值导致进位不明确，生成算法采用“前缀 + 固定位数序号”模型：`deviceBase` 和 `channelBase` 的最后 6 位作为序号窗口，前 14 位保持不变。设备数量必须不超过 `999999 - baseSequence`；当 Base 序号为 `000000` 时，当前设计最多支持 `999999` 台设备。

示例：

```text
deviceBase  = 34020000001110000000
channelBase = 34020000001310000000
index       = 0
deviceId    = 34020000001110000001
channelId   = 34020000001310000001
```

数字模式下 `domain` 仍用于 SIP URI 和 SSRC 生成，不参与设备/通道 ID 的拼接。这样可以明确区分 SIP 域和设备国标编号。

## 编号生成与唯一性

`IdentityFactory` 改为接收完整的身份配置，而不是只接收 `runID/prefix/domain`：

```go
type IdentityConfig struct {
    Mode        string
    DeviceBase  string
    ChannelBase string
    LegacyPrefix string
    RunID       string
    Domain      string
}
```

生成规则：

1. 校验 `index >= 0`。
2. 数字模式校验两个 Base 都是 20 位 ASCII 数字，并提取前 14 位和最后 6 位序号。
3. 将 `index + 1` 加到序号窗口，超过 `999999` 时返回 `numeric identity range exhausted`。
4. 设备 ID 和通道 ID 分别由各自的前缀与序号拼接，二者必须不同。
5. 流名继续使用 `<deviceId>_<channelId>`。
6. Call-ID 继续使用 `runID-index-random`，不使用设备编号作为唯一性来源。
7. SSRC 继续使用现有十位数字分配逻辑，并保留重复检测。

`IdentityFactory` 在内存中同时记录已生成的设备 ID、通道 ID 和 SSRC；重复时返回错误而不是覆盖已有身份。

## 兼容策略

- 如果 `identity` 未配置，默认使用 `numeric` 模式；此时必须提供 `deviceBase` 和 `channelBase`，配置校验会给出明确错误。
- 现有仅配置 `idPrefix: loadtest-` 的文件自动进入 `legacy` 模式，确保旧测试可以继续运行。
- 新配置推荐显式写出 `identity.mode: numeric`，避免测试人员误以为 `loadtest-*` 已经是标准国标编号。
- `legacy` 模式的校验与当前一致：前缀必须以 `loadtest-` 开头；文档明确说明该模式不适用于 WVP 严格设备 ID 校验。

## 运行时影响

- REGISTER 的 From、To、Contact 和 MESSAGE 的 From 用户名会自动使用数字设备 ID，无需修改 SIP 构造器接口。
- 通道 ID 变为 20 位数字后，WVP Catalog 同步、点播 URL 和流名均使用同一身份，不再出现设备 ID 与通道 ID 长度不一致的情况。
- `devices_started_total` 仍只表示设备对象启动；本次不扩展注册确认状态机。后续可单独增加 REGISTER 成功指标，但不作为本次改造范围。

## 错误处理

配置错误在启动前返回：

- 未知 `identity.mode`。
- 数字模式缺少 Base、长度不是 20 位或含非数字字符。
- `deviceBase` 与 `channelBase` 前 14 位/序号窗口不满足规则。
- `deviceCount` 超出序号窗口。
- 设备或通道编号重复。

运行中不应因为编号耗尽才创建部分设备；编号范围校验必须在 `Config.Load` 完成。

## 测试策略

- `IdentityFactory` 单元测试：数字模式生成 1、2、多个设备，验证 20 位纯数字、递增、设备/通道唯一和流名一致。
- 边界测试：`deviceCount=999999` 可通过，超过窗口失败；Base 为全零、含字母、长度错误时失败。
- 兼容测试：旧 `idPrefix: loadtest-` 配置仍能加载并生成 legacy ID；数字模式不再要求 `idPrefix`。
- 配置测试：显式 `identity.mode: numeric` 和缺省 identity 的行为符合兼容规则。
- 运行现有 Go 单元测试，并执行压测工具的 `go test ./...`。
