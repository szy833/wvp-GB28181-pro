# 设备集中退出 SIP 会话残留定位与复验

## 结论与范围

2026-10-11 在运行中的 WVP/ZLM 上，以修复后的候选工具再次进行两轮 10 路 TCP-PASSIVE 复现。两轮均正常注册、目录入库、点播、持续观看及跨素材循环解码，但集中退出后分别残留 3 条、1 条 SIP 会话，超过 30 秒验收窗口。

第二轮通过脱敏 SIP 抓取、WVP 实时日志接口和被动 Redis RESP 抓取，确认残留会话对应的 Redis 删除事务返回了事务中止。删除事务监视所有会话共用的 EXPIRE ZSET，导致不同会话并发清理也会相互冲突。该会话在正常退出阶段没有得到有效补偿，直到设备离线才被兜底删除。这是本次残留的已验证故障链路，不再只是基于日志猜测。

本轮仅诊断与复现，未修复生产代码、未部署或重启服务、未提交 Git。不扩大到 25/50/100 路，不修改 Redis/数据库中的现有记录，不触碰真实摄像头，不读取仓库外的日志或运行包，不操作 `t.cap`。保留新增测试设备记录。证据文件均在本仓库下。

运行 WVP 为 2.7.4、`ea38c55`，与当前源码及 `target/classes` 不同；该运行提交的 Git 对象不在仓库中。以运行时实际收发证据确认事务失败，以当前源码提供修复入口，不用当前源码替代运行版本。尤其不能声称本次运行一定是“三次重试耗尽”：残留会话在退出阶段只观察到一次中止的 EXEC，未观察到后续成功删除，具体重试为何未生效仍需核对运行包。

步骤：媒体基线归零与全新编号检查 → 注册与目录确认 → 设置 TCP-PASSIVE → 建立并持续观看 10 路 → 40 秒代表性解码 → 模拟设备同时停止媒体并发送 BYE → 30 秒资源收敛检查 → 被动观察设备离线兜底 → 最终资源与进程核验。

## 关键时序证据

以下为残留设备 05010 的闭环，SIP 使用 `packetTime`，Redis 使用报文时间，WVP 日志使用服务日志时间；不将采集缓冲后的落盘时间当作信令发送时间。

| 时间 | 事件 | 含义 |
|---|---|---|
| 12:14:44.423827 | 设备主动 BYE | 原 Dialog 的 Call-ID 与 Tag 关联一致 |
| 12:14:44.425162 | WVP 回复 200 | 收到并响应 BYE，不等于业务清理完成 |
| 12:14:44.427 | WVP 命中 SIP 会话 | 未因设备或会话不存在而提前退出 |
| 12:14:44.432 | WVP 命中 InviteInfo | 本轮媒体已经正常建立 |
| 12:14:44.446 | RTP owner 清理命中 | 媒体资源关闭正常 |
| 12:14:44.456391 | WATCH 本会话 DATA、STREAM 和共享 EXPIRE | 将本会话清理与所有会话的索引写入绑定 |
| 12:14:44.457181 | MULTI | 开始删除事务 |
| 12:14:44.457588 | EXEC | 提交删除事务 |
| 12:14:44.457981 | Redis 返回 nil array | WATCH 冲突导致整个事务中止，删除未执行 |
| 12:15:16 | 探针退出 | 30 秒清理窗口仍有 1 条会话，报告 FAIL |
| 12:15:41.809 | WVP 设备离线日志 | 开始设备离线兜底路径 |
| 12:15:41.818772 | 再次 EXEC | 对同一 Call-ID 执行删除 |
| 12:15:41.818930 | 返回 5 项事务结果 | 离线兜底删除成功 |

正常 BYE 到有效兜底删除约 57.4 秒。第一轮工具看到的 3 条残留也在较后的删除事务中清掉。

完整采集共记录 25 个 V2 EXEC，20 个正常数组结果、5 个事务中止。正常结果包含 10 次会话创建，不能将 20 全部说成删除次数。异常删除中有的被媒体离开等后续路径清掉；05010 在验收窗口内只有中止记录，没有任何成功删除。最终 5 次事务冲突不等于 5 条会话残留。

在 05010 的 WATCH 和 EXEC 之间，另一个不同 Call-ID 的删除事务已提交成功，且也监视同一个 EXPIRE key。本会话 DATA/STREAM 是独立键，但共享 ZSET 被其他会话的 ZREM 修改，足以使 WATCH 失效。Redis WATCH 监视的是整个 key，不是 ZSET 的某个 member。

该故障机制可以表示为：

```text
会话 A：WATCH(DATA_A, STREAM_A, EXPIRE_全局)
会话 B：删除自身会话，ZREM(EXPIRE_全局, callId_B)，提交成功
会话 A：EXEC -> nil，整个删除事务被撤销
会话 A：正常退出阶段未有效补偿 -> 留存至设备离线兜底
```

这不是尚未回 ACK、媒体时间轴不连续、停止接口返回结构误解析，也不能由工具收到 200 后关闭 SIP socket 来解释 Redis 已明确中止的删除事务。工具退出先关闭媒体，仍可能放大清理交叉时序，但修复需要覆盖这种正常/异常退出交错，不应通过降低退出并发或放宽验收时间掩盖问题。

## 当前源码中的修复入口

1. `src/main/java/com/genersoft/iot/vmp/gb28181/session/SipInviteSessionManager.java:265`：`removeByCallId()` WATCH 共享 `expireKey()`，不同会话的删除会发生不必要的冲突。
2. `src/main/java/com/genersoft/iot/vmp/gb28181/session/SipInviteSessionManager.java:514`：事务内部对共享 ZSET 执行 ZREM，这本身可以与其他 member 的修改共存，不应因此要求整个 ZSET 内容保持不变。
3. `src/main/java/com/genersoft/iot/vmp/gb28181/session/SipInviteSessionManager.java:518`：当前实现最多重试 3 次；只有抛异常且重试耗尽才打印错误，普通 WATCH 冲突耗尽会静默返回 false。
4. `src/main/java/com/genersoft/iot/vmp/gb28181/session/SipInviteSessionManager.java:264`：`removeByCallId()` 忽略上述布尔结果，调用者无法得知清理失败。
5. `src/main/java/com/genersoft/iot/vmp/gb28181/transmit/event/request/impl/ByeRequestProcessor.java:306`：finally 调用删除，只能捕获抛出的异常，无法感知静默失败。

注意：当前源码最多三次重试的实现及仓库内旧包依赖已检查，但不是运行包证据。Spring Data Redis/Lettuce 对中止结果的 null/空列表转换也受版本和配置影响，应在实际目标依赖上覆盖测试；本轮没有证据证明运行时误把空列表当成功，不能将这个推测当成已确认根因。

## 建议修复与验收方案（尚未实施）

优先修复会话存储层，而不是延迟关闭模拟设备或增加清理等待时间：

1. 按 Call-ID 删除只对本会话 DATA、STREAM 及必要 META 做 owner/version 校验，不 WATCH 全局 EXPIRE。仍在同一个事务中 DEL、SREM、ZREM，保持索引清理原子性；保留旧会话不能删除新 stream owner 的约束。
2. 对所有事务结果区分成功、WATCH 冲突、异常和真正的无需操作；失败不得静默作为删除成功返回。设置有限重试，并将耗尽结果通过异常或明确结果反馈给调用者，日志关联操作、Call-ID、重试次数。
3. 增加有界且可观测的失败清理补偿。只清理确定的旧 Call-ID，不能仅凭 stream 删除后来重建的会话。设备离线和七天安全 TTL 不应成为正常退出的唯一补偿。
4. 一并审查 `removeExpiredIfOwner()` 和 `touchIfNeeded()` 对全局 EXPIRE 的 WATCH；过期判断需要保留每个 Call-ID 的 deadline/version 验证，不能机械删除 WATCH 后误删刚续期会话。
5. 在确定运行版本或部署经过验证的候选包后，先复测 10 路集中退出及并发平台停止，再恢复 25/50/100 路。部署和重启需另行安排，不在此次定位请求中实施。

自动化回归必须覆盖：不同 Call-ID 同时删除互不冲突、同一 Call-ID 幂等删除、旧 Call-ID 不删除新 owner、WATCH 冲突重试及耗尽可观测、异常时连接事务状态复原、活跃会话续期与过期清理并发、BYE 与媒体离开重复清理。

真实环境验收要求至少三轮同规模集中退出均在原 30 秒窗口内会话/流/listener 归零；不能等待设备离线再算正常退出通过。之后才进行更大负载和持续运行测试。此次已复现故障，不是修复后验收通过。
