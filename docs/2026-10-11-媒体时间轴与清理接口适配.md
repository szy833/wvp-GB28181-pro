# 媒体时间轴与清理接口适配

## 范围与证据

仅修复 `tools/gb28181-load-test`，不修改或重启 WVP/ZLM，不增加并发。
此前 TCP/UDP 单路流均可到达，但 FFmpeg 解码时间停在 0.64 秒，出现非单调 DTS；本地读取同一样本正常。
样本为 MPEG-1 pack/PES（385 个 pack，413 个视频 PES，其中 18 个无时间戳），首轮发送保留原始字节，异常在首次循环之前发生。

## 定位和实现步骤

1. 单路 A/B：仅将同一样本重封装为 MPEG-2 PS，不改变视频编码、发送器、服务配置，检查 ZLM 输出时钟；结果决定是否需要规范化 PS/PES。
2. 为确认的媒体封装问题及清理接口真实响应新增失败回归测试，再做最小范围修复。
3. 清理检查支持 WVP 的直接数组及 `data.data`/`count` 包装；支持 ZLM `code=0` 且省略 data 的空 listener 响应。非成功状态、null、错误结构、无效记录必须报错，不能被计为零残留。
4. 本地全量测试、竞态检测、静态检查后构建独立候选版本；使用新设备 ID 单路验证 TCP、UDP 和跨文件循环。

## 集成测试风险与保护

测试会新增虚拟设备/通道数据库记录及短时媒体录像；设备 ID 必须先检查不存在。保留原二进制、样本及历史报告。测试前媒体/listener 基线必须为空，空闲磁盘低于 4 GiB 则终止。只停止本次虚拟设备，不调用全局删除或关闭接口。私有配置权限 0600，不提交凭据。FFmpeg 输出帧数或退出码 0 不能替代时间轴验收。没有 Prometheus 时，不作容量极限结论。

## 结果

### 根因确认

旧素材封装与当前 ZLM 的时间戳处理不兼容，而不是 TCP 专属问题或单纯循环时钟平移错误。仅将同一 H.264 重封装为 MPEG-2 PS，旧发送器的输出时间就从停在 0.64 秒变为推进至 8 秒，但仍出现大量重复 DTS 警告。因此只把 FFmpeg `mpeg` 改成 `vob` 不足以解决问题。通用 muxer 会将多个帧聚合到 PES 中，并不是每个视频帧都有独立时间戳。

修复通过离线生成明确的逐帧格式消除歧义：FFmpeg 转为 CFR、无 B 帧、每帧带 AUD 的 H.264/yuv420p；工具写 MPEG-2 pack、视频 system header、H.264 PSM（含 CRC-32/MPEG-2）及有界 PES。每帧独立 PTS，大帧的所有 PES 使用同一 PTS。循环时仍平移 SCR、PTS/DTS，RTP 时钟持续递增。启动前校验每组时间戳恰好一个 AUD，拒绝 MPEG-1、无时间戳视频 PES 和聚合帧素材，不猜测缺失帧的时间。

清理检查新增 WVP 的 `{"code":0,"data":{"data":[],"count":0}}` 包装支持，保留直接数组格式；验证 count 与数组长度一致。支持 ZLM `listRtpServer` 的 `{"code":0}` 空列表响应，但拒绝缺失/错误 code、显式 null、错误数据类型、缺少标识的记录。WVP 平台会话可无 deviceId，通过 streamId 校验及范围匹配。仍要求连续两次有效零残留采样，不将接口不可用当成清理成功。

### 真实环境阶段与步骤

证据目录：`tools/gb28181-load-test/reports/media-adaptation-20261011/`。
诊断入口：`reports/retest-20261011/media-adaptation-probe.py`，复用已验证的单设备探测流程。每阶段先核对新设备 ID 和空媒体基线，再从运行时接口生成权限 0600 的私有配置；注册后仅修改本次虚拟设备的传输模式，等待目录和点播，按 2 秒采样，使用 FFmpeg 读取对应 RTSP 流，最后核对资源释放。

### 遗留边界与使用方式

- 原二进制及样本未替换；使用新候选时必须将配置 `media.file` 指向 `./media/sample-v2.ps`，否则旧素材会明确报错。已更新 README 和使用手册。
- 保留三个新增虚拟设备/通道数据库记录，未调用删除设备接口；探测结束时在线状态尚未由 WVP 的保活超时任务更新。后续只读复核三台均已离线，WVP 会话总数为 0，本次工具及对应 RTSP 解码进程均已退出。
- 本次仅单设备串行验证，未增加并发、未修改服务配置、未重启服务、未触碰真实摄像头或历史抓包。
- 新素材生成依赖支持 libx264 的 FFmpeg，运行压测不需要 FFmpeg 或 Go；每次生成会转码，不保证原视频码率及编码参数不变。
- 监控未接入 CPU、JVM、Redis、宿主网络等资源数据，容量结论仍为 `INCONCLUSIVE`。本次证明两项功能修复，不证明大规模容量上限或多种 ZLM 版本均兼容。
