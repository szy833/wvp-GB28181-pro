# WVP GB28181 项目结构与开发协作指南

**文档日期：** 2026-07-30
**适用范围：** 后续代码开发、问题排查、性能优化和多 agent 协作
**项目目录：** `/data/shizy/wvp-GB28181-pro`

## 1. 项目定位

本项目是 WVP-Pro 的 GB28181 视频管理平台，负责设备注册、目录/状态查询、实时点播、回放、下载、语音对讲、平台级联、RTP 收流和 ZLMediaKit（ZLM）媒体分发。它同时提供后端 HTTP API 和 Vue 管理前端。

主要技术组成：

- 后端：Java、Spring Boot、Spring MVC、MyBatis、Redis、SIP 协议栈。
- 媒体：ZLMediaKit，WVP 管理 RTP 接收端口并通过 HTTP Hook 感知流状态。
- 数据：MySQL/PostgreSQL/H2 脚本位于 `数据库/`，Redis 保存运行时会话、InviteInfo 和索引。
- 前端：`web/` 下的 Vue/webpack 工程。
- 部署：`docker/`、`bin/`、`run.sh` 和 `install.sh` 提供容器或本机运行辅助。

项目中的“信令成功”“SIP 会话已建立”“收到媒体”“对外点播成功”是不同事件，排障时不能用单条日志或单个状态代替完整流程。点播的可靠成功条件见 [GB28181点播InviteInfo状态与媒体确认流程.md](GB28181点播InviteInfo状态与媒体确认流程.md)。

## 5. GB28181 业务总览

### 5.1 注册和保活

```text
设备 -> SIP REGISTER -> SipLayer/SIPProcessorObserver
     -> 注册处理器更新设备在线状态和 Contact
设备 -> MESSAGE Keepalive/Status/Alarm
     -> MessageRequestProcessor 及 notify handler
     -> 更新设备状态、目录或告警
```

设备离线时，`DeviceServiceImpl` 除了更新数据库在线状态，还要根据设备索引清理该设备的 SIP Invite 会话、RTP 资源和播放状态。

### 5.2 目录和设备查询

WVP 通过 SIP MESSAGE 的 Catalog、DeviceInfo、DeviceStatus 等命令和异步响应维护设备/通道数据。业务 API 通常从数据库返回目录；实时状态由 SIP 通知刷新。修改目录处理时要同时考虑 SN、设备 ID、通道 ID、异步响应超时和重复通知。

### 5.3 实时点播

```text
PlayController
  -> PlayServiceImpl.play()
  -> RtpServerServiceImpl.openGbRTPServerForPlay()
  -> RtpResourceContext: REGISTERING -> WAITING_MEDIA
  -> InviteInfo=ready
  -> SIPCommander.playStreamCmd() 发送 INVITE
  -> 设备 200 OK / WVP ACK
  -> SipInviteSessionManager.put(SsrcTransaction)
  -> InviteInfo 先更新为 ok（streamInfo 可能为空）
  -> 设备发送 RTP
  -> ZLM /on_stream_changed(register)
  -> MediaArrivalEvent -> on_media_arrival
  -> RtpResourceContext: WAITING_MEDIA -> SUCCESS
  -> onPublishHandlerForPlay() 补充 streamInfo
  -> 通道置为播放中并执行点播成功回调
```

`/on_publish` 只表示 ZLM 推流鉴权允许，不是媒体成功；必须结合 `streamInfo`、RTP 资源 `SUCCESS` 和成功回调判断真实可播放状态。完整说明见专项文档。

### 5.4 回放和下载

回放与点播共享 RTP 资源、InviteInfo 和 SIP 会话管理，但 SDP/命令中会增加时间段、录像文件或下载语义。回放暂停、恢复、倍速和拖动通过 SIP INFO 控制，需要从 `SipInviteSessionManager` 按 stream 取回原始 `SipTransactionInfo`。下载结束可能由设备 MESSAGE 通知，按 Call-ID 关联下载会话后再清理资源。

### 5.5 停止和设备 BYE

```text
停止 API 或点播超时
  -> 查询 InviteInfo 和 SsrcTransaction
  -> SIP 200 OK 后尝试发送 BYE
  -> 删除 InviteInfo
  -> 关闭 RTP 资源
  -> removeByStream()/removeByCallId()

设备主动 BYE
  -> ByeRequestProcessor 读取 Call-ID
  -> sessionManager.getSsrcTransactionByCallId()
  -> 按 PLAY/PLAYBACK/DOWNLOAD/TALK/BROADCAST 分支
  -> 停止通道、关闭 RTP、清理 InviteInfo
  -> finally 中 removeByCallId() 兜底
```

### 5.6 语音对讲和平台级联

- 对讲：使用 `SIPCommander.talkStreamCmd()`、`PlayServiceImpl.talk()/stopTalk()`，会话类型为 `TALK`，停止时仍需释放 SIP、RTP 和媒体资源。
- 平台级联：`PlatformServiceImpl` 和 `SIPCommanderForPlatform` 负责上级平台广播、点播、停止和 SSRC 修正，会话类型可能为 `BROADCAST`；平台会话不能混入设备离线索引。
- 级联异常时优先按 Call-ID/stream 清理，不要仅按设备 ID 删除，因为平台会话通常没有设备 ID。

## 6. RTP、ZLM 和状态闭环

RTP 资源状态机由 `RtpResourceContext` 管理，典型状态如下：

```text
REGISTERING -> WAITING_MEDIA -> SUCCESS
       \-> FAILED/TIMEOUT/CLOSED
```

- `REGISTERING`：正在创建监听器和 Hook。
- `WAITING_MEDIA`：端口已监听，等待设备 RTP 或 ZLM 流变化事件。
- `SUCCESS`：已收到媒体到达事件并执行成功回调。
- `TIMEOUT/FAILED/CLOSED`：超时、初始化失败或业务主动释放。

媒体事件链：

```text
ZLM /on_publish
  -> 鉴权允许
ZLM /on_stream_changed(register)
  -> ZLMHttpHookListener 发布 MediaArrivalEvent
  -> HookSubscribe 分发 on_media_arrival
  -> RtpServerServiceImpl 找到 app+stream+mediaServer
  -> RtpResourceContext.onMediaArrival()
  -> PlayServiceImpl 补充 StreamInfo 并回调业务
```

媒体 Hook 和 SIP 会话是两条并行链路：SIP 200 OK 可以先于 RTP 到达；RTP 到达也不能替代 SIP Dialog 的 Call-ID 管理。任何修复都要同时验证信令、RTP 资源、ZLM 流和业务状态四个层次。

## 7. InviteInfo、SipInviteSessionManager 和 Redis

### 7.1 InviteInfo

`InviteInfo` 记录点播/回放/下载业务状态、设备/通道、SSRC、RTP 端口、媒体服务器和 `StreamInfo`，由 `InviteStreamServiceImpl` 持久化。常见状态含义：

```text
ready = RTP 资源准备好，SIP 或媒体尚未完成
ok    = SIP 200 OK 已建立，或媒体成功后再次确认；不能单独代表有画面
```

Redis 读写应优先使用按 stream、SSRC 等索引，避免在热路径对全量 Hash 做 `HSCAN/HVALS`。全量管理接口和迁移任务可以分批扫描，但必须设置批量上限和监控。

### 7.2 SipInviteSessionManager

该管理器保存 `SsrcTransaction`，建立以下关联：

```text
Call-ID <-> app + stream <-> device/channel/mediaServer
```

当前 V2 数据结构和迁移规则详见 [sip-invite-session-manager-usage.md](sip-invite-session-manager-usage.md)。开发时遵守：

- 写入主记录和派生索引必须保持一致，删除必须做 owner 校验。
- 业务查询使用 `getSsrcTransactionByStream()`、`getSsrcTransactionByCallId()` 或 `getSsrcTransactionByDeviceId()`，不要自行扫描全量 Redis Hash。
- 异常路径、BYE、设备离线、媒体服务器下线和超时任务都必须有删除或 TTL 兜底。
- `SsrcTransaction` 存在只代表 SIP 会话可关联，不代表 RTP 已收到。

### 7.3 Redis 与数据库边界

- 数据库保存设备、通道、平台和业务配置等持久数据。
- Redis 保存 InviteInfo、SIP 会话、索引、过期任务和跨实例协调等运行时数据。
- Redis 清理不能替代数据库状态恢复；业务停止时应按顺序更新业务状态、释放媒体、清理会话索引。
- 多实例部署必须使用 `serverId` 隔离运行时 Key，并验证 Redis、SIP 和媒体服务器的实例归属。

## 8. 排障路径

### 8.1 点播无画面

按以下顺序采集证据：

1. HTTP 点播请求是否进入 `PlayController` 和 `PlayServiceImpl.play()`。
2. 是否创建 RTP 监听端口，`RtpResourceContext` 是否进入 `WAITING_MEDIA`。
3. SIP INVITE 是否发出、设备是否返回 100/200、ACK 是否送达。
4. `SipInviteSessionManager` 是否保存 Call-ID、stream 和 SSRC。
5. ZLM 是否收到 RTP，是否出现 `/on_publish` 和 `/on_stream_changed(register)`。
6. `RtpResourceContext` 是否进入 `SUCCESS`，是否构造 `StreamInfo` 并执行点播成功回调。

如果只有 `InviteInfo.status=ok`、只有 `/on_publish` 或只有 SIP 200 OK，均不能直接判定媒体可播放。

### 8.2 UDP 不通、TCP 被动可用

UDP 和 TCP 是不同的网络路径。分别检查：

- WVP SDP 中宣告的 `media.sdp-ip`、端口是否是摄像头可达地址。
- Windows 宿主机、虚拟机 NAT/桥接、防火墙和端口转发是否允许摄像头到 WVP/ZLM 的 UDP 入站。
- RTP 端口范围是否在虚拟机和防火墙中放行，是否与其他进程冲突。
- ZLM 的 `media.hook-ip` 回调方向是否可达；Hook 可达不等于 RTP UDP 可达。
- 用 `t.cap` 或同等抓包确认 INVITE/200/ACK、RTP/UDP、ZLM Hook 的实际源/目的 IP 和端口。

TCP 被动收流成功只能证明 TCP 监听和设备到 TCP 端口的路径可用，不能排除 UDP 路由、NAT 或防火墙问题。

### 8.3 收到 BYE 或等待超时

记录 Call-ID、CSeq、From/To Tag、设备/通道、InviteInfo 状态、RTP 状态和媒体服务器。确认 BYE 是设备主动发送、WVP 超时清理还是媒体服务器下线触发。若主动 BYE 问题暂不处理，也必须确认清理是否幂等、Redis 会话是否最终删除、RTP 端口是否释放。

涉及 SIP/RTP/Redis 的改动，最低验收边界：

- 正常点播：`ready -> SIP 200 OK -> session 保存 -> 媒体到达 -> RTP SUCCESS -> streamInfo`。
- 无媒体超时：关闭 RTP、删除 InviteInfo、删除 SIP 会话索引且不误删新会话。
- 设备主动 BYE：按 Call-ID 找到正确业务并完成幂等清理。
- 设备离线：只清理该设备会话，不误删平台级联会话。
- Redis 异常或重复回调：不会留下不可回收的主记录/索引组合。

### 9.1 真实环境集成测试待办与风险

以下项目已完成代码级修复和定向测试，但必须在真实 ZLM/GB28181 环境中集中验证：

- 多端口 RTP 创建时，ZLM RTP listener 使用八位大写十六进制 SSRC，业务发布流使用业务 stream。
- Play 超时、设备 BYE、设备离线、重复关闭、媒体节点上线和平台广播停止后，listener 与业务流均被释放。
- 旧 `resourceId`、旧 SSRC 或旧 InviteInfo 不会关闭新 owner 的 listener 或业务流。
- SSRC 修正时，`updateRtpServerSSRC` 使用真实 ZLM listener stream，不使用业务 stream。
- 语音对讲、创建失败、超时、BYE、设备离线和显式停止后，内部 SSRC lease 均已释放；随机 SSRC 并发分配不产生重复值。
- ZLM 媒体列表对账失败或尚未成功时，RTP 节点会记录原因并暂停自动 SSRC 分配；恢复后才重新放行。需验证空列表、ZLM 超时/异常和恢复场景。
- 关闭前后通过 ZLM `listRtpServer` 核对 listener 实际存在和消失，不能只依据 WVP 侧无异常日志判断关闭成功。
- 记录 ZLM 版本、媒体节点配置、设备/平台类型、测试步骤、请求参数、ZLM 返回结果和残留资源。

当前风险等级：条件性高风险。若缺少真实 ZLM 对账，无法证明 listener 已实际释放、SSRC 占用快照与服务端一致，可能存在端口泄漏、旧会话误清理或分配暂停风险。

性能验收应记录 Redis CPU、命令耗时、网络流量、会话数量、并发点播量和清理延迟；不能只以单次接口响应时间作为结论。专项压测记录见 `docs/superpowers/specs/2026-07-30-sip-invite-session-load-test-record.md`。

## 10. 多 agent 协作规则

### 10.1 开始前

1. 只能在 `/data/shizy/wvp-GB28181-pro` 内读写和执行命令。
2. 先阅读本指南、相关专项文档和根目录 `AGENTS.md`。
3. 执行 `git status --short`，识别用户已有改动；不要覆盖、回滚或提交不属于本任务的文件。
4. 明确修改范围、验收边界和是否需要线上压测；跨模块改动先写方案。

### 10.2 修改中

- 按模块划分边界：SIP 信令、RTP/媒体、InviteInfo/Redis、数据库、前端尽量由不同 agent 负责，避免同时编辑同一文件。
- 修改共享模型、Key 或状态机时，先通知其他 agent，并同步更新文档和测试。
- 代码注释只解释非显然的并发、幂等、owner 校验或状态转换原因。
- 不要用全量扫描替代索引查询；不要在热路径加入无上限日志或网络调用。
