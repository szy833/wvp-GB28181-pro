## 5. 授权后的现场诊断与根因

### 5.1 三次快照一致

对同一 PID `17835` 执行三次 `Thread.print -l` 和 `Thread.dump_to_file -format=json`。原始快照保存在仓库内 `target/diagnostics-18080-20261014/`，不纳入提交；JSON 快照权限为 0600。

| 快照 | 北京时间 | Tomcat handler 数 | 载体数 | pinned 数 | 日志写锁等待 | Okio 锁等待 |
| --- | --- | ---: | ---: | ---: | ---: | ---: |
| 1 | 2026-10-14 10:02:16 | 8193 | 16 | 16 | 14 | 2 |
| 2 | 2026-10-14 10:03:08 | 8193 | 16 | 16 | 14 | 2 |
| 3 | 2026-10-14 10:04:34 | 8193 | 16 | 16 | 14 | 2 |

三次相隔约 138 秒，16 个 carrier 承载的虚拟线程 ID 及完整调用栈完全相同，均包含 `VirtualThread.parkOnCarrierThread`，且全部经过 `RtpResourceContext.close()`。

Tomcat handler 数是线程数，不等同于实际 socket 数。最后一次快照中 220 个 handler 有可见栈，7973 个为空栈；线程转储不提供这些空栈线程的完整调度状态，因此不将每个空栈都单独断言为某一种业务等待。载体耗尽的判断来自 16 个载体及其实际承载线程的逐项关联，而不是来自空栈计数。

### 5.2 直接阻塞点

- 14 个载体所承载的线程：`VirtualThread.parkOnCarrierThread -> ReentrantLock.lock -> OutputStreamAppender.writeBytes`，上层为 RTP 状态日志或媒体关闭日志。
- 2 个载体所承载的线程：`VirtualThread.parkOnCarrierThread -> ReentrantLock.lock -> AsyncTimeout.scheduleTimeout/cancelScheduledTimeout -> ResponseBody.string -> ZLMRESTfulUtils.sendPost -> closeStreams`。
- 平台线程 `Okio Watchdog` 也停在同一超时管理路径的锁重新获取上，不能把媒体 read timeout 视为一定会按时解除阻塞的保障。
- Tomcat `http-nio-18080-Acceptor` 停在 `LimitLatch.countUpOrAwait -> AbstractEndpoint.countUpOrAwaitConnection`，表明达到连接限额后暂停接收；不是监听 socket 已关闭。
- 监听 backlog 仍为 101/100，版本接口复测仍超时。

### 5.3 代码及实际部署包确认

关键源码为 `src/main/java/com/genersoft/iot/vmp/service/bean/RtpResourceContext.java:300`：

```java
public synchronized boolean close(String reason) {
    // ...
    if (state.compareAndSet(current, RtpResourceState.CLOSED)) {
        logStateTransition(current, RtpResourceState.CLOSED, reason);
        runCleanup(terminalCleanup);
        return true;
    }
    // ...
}
```

日志及外部清理均在 Java monitor 持有期间执行。`terminalCleanup` 经 `RtpServerServiceImpl.closeOwnedMediaResources()` 调用媒体 HTTP 接口；载体实际堆栈也确认此链路，而非仅根据源码推测。

只读提取实际部署 `wvp-pro-2.7.4-10120509.jar` 中的 `RtpResourceContext.class` 到仓库内诊断目录，用 `javap -c -p` 确认该部署方法确为 `synchronized`，且在方法内依次执行日志和清理。没有用“当前源码与部署必然相同”的假设代替部署核验。

实际运行条件：JDK `21.0.2+13-58`，虚拟线程开启；包内依赖 Logback 1.5.18、OkHttp 4.12.0、Okio JVM 3.6.0、Tomcat 10.1.39。包内日志配置直接关联同步 Console/File appender，没有 AsyncAppender 包装。

**当前故障机制已确认：同步 monitor 范围内的日志/媒体 HTTP 锁等待造成 Java 21 虚拟线程 pinning，16 个载体持续耗尽，HTTP 请求无法继续调度和完成；连接积压进一步触发 Tomcat 连接限额与 backlog 饱和。**

这一机制解释了 CPU 不必很高、进程和端口仍存在，但整个 HTTP 控制面无法响应。不是普通平台线程池大小不足，也不能靠提高 accept backlog 或 max-connections 根治。

## 6. 恢复和修复建议（未执行）

1. **代码修复优先方向**：把 `close()` 的状态认领/一次性标记与日志、HTTP 清理分开，缩短 monitor 范围；同时审计成功/失败及其他同步回调路径。必须保留一次性清理、owner/epoch 隔离、并发关闭的完成语义，不能简单删除 `synchronized` 后直接上线。
2. **临时缓解方向**：若需先恢复，可评估关闭 Spring 虚拟线程并重启，但平台线程仍会受阻塞影响，不能宣称这是完整修复。运行配置修改、重启及残留资源处理需另行确认；当前未执行。
3. **运行时方向**：可评估升级到支持同步 monitor 解除虚拟线程 pinning 的较新 JDK（JDK 24 起），但需项目兼容性及集成回归，不把升级当成免除阻塞 I/O 治理的保证。
4. **防护方向**：媒体调用隔离为有界、可监控的执行通道，设置并验证端到端截止时间；优化日志执行路径，避免同步区内输出。异步日志队列满时的阻塞策略也要验收，不能只加 AsyncAppender 就保证没有 pinning。
5. **集中验收**：隔离复现 300 路并发停止、日志锁竞争、媒体超时/慢响应和重复关闭；持续观测健康接口延迟、carrier pinning、连接数/CLOSE_WAIT、清理待办及 SIP/RTP/SSRC 终态。跨线程变化需覆盖并发代次隔离与资源清理回归。
