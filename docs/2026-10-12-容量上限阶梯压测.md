# WVP 媒体并发容量上限阶梯压测报告

## 1. 结论

本报告回答“之前的 100 路是否为同时点播，以及当前环境可以稳定跑多少路”两个问题。

- 100 路是同时保持的 100 路逻辑点播流，不是 100 次串行请求；每路均完成 REGISTER、目录就绪、INVITE、RTP 媒体确认、观看、停止和终态回收。
- 在本次部署、素材、同机压测口径下，**已验证的稳定容量为 200 路同时点播**。150 路和 200 路均完成三轮完整流程、解码核验、主动 BYE 和三次独立终检。
- 300 路不是稳定容量：40 路/秒启动时第三轮 300 路中有 12 路点播启动失败；20 路/秒启动时第二轮停止窗口出现 5 次真实远端 `broken_pipe` 和 4 次本地取消，随后清理/终态探针超时。
- 300 路测试之后，WVP 进程仍在，但 `/api/server/version` 在 5 秒内无响应；因此没有继续执行 250 路或 500 路，避免在控制面失去响应时继续扩大残留和风险。
- 200 路是当前环境的安全基线，不是硬件理论上限。250～300 路之间的精确边界需要先恢复 WVP、排空旧会话，再进行单独的二分或小步阶梯测试。

## 2. 测试环境

| 项目 | 实测配置 |

| 内存 | 15 GiB，Swap 0 |

| 内核 | Linux 3.10.0-1160.el7.x86_64 |
| 文件句柄 | `ulimit -n=999999` |
| WVP | 2.7.4，构建时间 `2026-10-12T13:09:28+08:00`，commit `3c2d3eb` |
| ZLMediaKit | 新部署版本，commit `b91e75e` |
| Redis | 与 WVP 同一测试环境；报告不记录连接凭据 |
| 压测位置 | 压测工具、WVP、ZLM、观看/解码端共用同一台主机，主机还有其他工作负载 |
| 测试素材 | `sample-v2.ps`，约 0.209 Mbps；素材循环并重写时间轴，确保跨循环可解码 |
| 测试模式 | GB28181 TCP-PASSIVE；每级最多三轮，包含全路观看、首末路 RTSP 解码、重复停止、主动 BYE 和终态清理 |

本环境不是独立的生产基准机：生成器和服务争用同一 CPU、内存、磁盘、网络和 Redis。因此资源指标用于解释本次边界，不应直接等同于另一台机器的容量。

## 3. 判定标准

只有同时满足以下条件才记为“稳定通过”：

1. 本轮计划点播全部成功，SIP `INVITE` 和媒体确认成功率为 100%。
2. 全路观看请求成功，抽样 RTSP 解码无错误。
3. 停止、主动 BYE 和重复停止均完成，不能用超时或本地取消掩盖真实错误。
4. Invite、SQL 通道、SIP 会话、RTP listener、媒体协议条目、SSRC 预留和待办索引全部归零。
5. 独立只读终检连续三次稳定，且不依赖“清理成功”覆盖原始业务失败。

### 4.1 100 路详细结果

- 3 轮共 300/300 点播成功，P95 启动耗时 0.304 秒，最大 0.489 秒。
- 6 次 RTSP 解码共 6036 帧，错误日志 0 字节。
- 清理收敛 2.944～3.339 秒；100 次主动 BYE 全部确认。
- 300 个 Invite、100 个 SQL 通道及活动资源三次独立终检归零。
- 进程 RSS 峰值：WVP 约 1195.93 MiB，ZLM 约 120.10 MiB；单核口径 CPU 峰值均可达到 100%，不代表整机 16 vCPU 饱和。

证据：[100 路报告](../tools/gb28181-load-test/reports/invite-lifecycle-20261011-stair-100-zlmfix-20261012-r1/test-report.md)。

### 4.2 150 路详细结果

- 3 轮共 450/450 点播成功，P95 启动耗时 0.233 秒，最大 0.330 秒。
- 6 次 RTSP 解码共 6036 帧，错误日志 0 字节；清理收敛 3.312～3.962 秒。
- 150/150 主动 BYE 成功，450 个 Invite 和 150 个 SQL 通道独立终检归零。
- WVP RSS 峰值约 1238.88 MiB，ZLM RSS 峰值约 162.59 MiB。

证据：[150 路报告](../tools/gb28181-load-test/reports/invite-lifecycle-20261011-capacity-150-20261012-r2/test-report.md)。

### 4.3 200 路详细结果

- 3 轮共 600/600 点播成功，P95 启动耗时 0.388 秒，最大 0.839 秒。
- 6 次 RTSP 解码共 6036 帧，错误日志 0 字节；清理收敛 4.532～7.589 秒。
- 200/200 主动 BYE 成功，600 个 Invite 和 200 个 SQL 通道独立终检归零。
- WVP RSS 峰值约 1472.64 MiB，ZLM RSS 峰值约 200.79 MiB。

证据：[200 路报告](../tools/gb28181-load-test/reports/invite-lifecycle-20261011-capacity-200-20261012-r1/test-report.md)。

### 4.4 300 路失败分类

#### 40 路/秒

第三轮计划 300 路，实际 288 路成功、12 路启动失败；当时工具版本只保留异常类型，未保留 12 个 HTTP 失败响应体，因此不能臆测是单一 HTTP、Redis、SIP 或 RTP 原因。该轮随后约 22.03 秒完成兜底清理，三次独立终检归零；“资源最终归零”不改变“业务启动失败”的判定。

证据：[300 路 40/s acceptance](../tools/gb28181-load-test/reports/invite-lifecycle-20261011-capacity-300-20261012-r2/acceptance.json)。

#### 20 路/秒

第二轮停止窗口出现 5 个设备的 RTP 写入错误，分类均为远端关闭：

```text
kind=remote_close
code=broken_pipe
error=peer closed or reset connection
cancelled=false
```

另有 4 次 `kind=local_cancel`，属于本地来源取消，不等同于远端网络错误。该轮采样曾出现 `active=300, pending=40, playing=260, listeners=261, mediaEntries=1330, ssrcReservations=300`；最终兜底停止和独立探针超时，`cleanupVerified=false`。WVP/ZLM 进程未退出且没有新增 core，但控制面随后无响应。

证据：[300 路 20/s acceptance](../tools/gb28181-load-test/reports/invite-lifecycle-20261011-capacity-300-20261012-r3/acceptance.json) 和同目录 `simulator.details.csv`、`simulator-metrics.jsonl`。

## 5. WVP 控制面退化证据

300 路失败后，WVP PID `17835` 和 ZLM PID `12471` 仍存活，但在 5 秒超时内访问：

```text
GET http://127.0.0.1:18080/api/server/version
```

未获得响应。WVP 进程当时约 1.53 GiB RSS、约 107 个平台线程，同时存在约 3142 个 `tomcat-handler-*` 虚拟线程；线程诊断显示大量线程停留在 Redis `hGet`、`SocketInputStream`、`getMediaList`、Invite 清理和 `parkNanos` 路径。该证据支持“控制面请求/清理依赖发生堆积或阻塞”的判断，但不足以在不重启、不进一步采样的情况下断言唯一根因。

诊断文件：

- [WVP jstack](../tools/gb28181-load-test/target/invite-lifecycle-check/zlm-core-20261012/wvp-jstack-after-capacity.txt)
- [WVP Java 线程快照](../tools/gb28181-load-test/target/invite-lifecycle-check/zlm-core-20261012/wvp-threads-after-capacity.json)
- [当前健康探针结果](../tools/gb28181-load-test/target/invite-lifecycle-check/zlm-core-20261012/wvp-version-after-capacity-current.txt)

旧 ZLM core 仍只有此前已分析的文件，没有在本轮 150～300 路测试中新增 core；本报告不把“无新增 core”当作容量通过条件。

## 6. 按媒体码率换算

本轮素材约 0.209 Mbps，理论原始媒体带宽约为：

| 同时逻辑流 | 原始媒体带宽（不含 RTP/IP/TCP 开销） |
|---:|---:|
| 100 | 20.9 Mbps |
| 150 | 31.35 Mbps |
| 200 | 41.8 Mbps |
| 250 | 52.25 Mbps |
| 300 | 62.7 Mbps |

真实摄像头通常码率更高，且会增加编码复杂度、关键帧突发、网络包数和磁盘/转封装压力。因此不能用本次 0.209 Mbps 素材直接承诺同硬件可稳定承载相同数量的高码率摄像头。

## 7. 对部署容量的建议

- 对与本次相同的 16 vCPU/15 GiB、低码率素材和同机压测条件，建议生产容量先按 **不超过 200 路同时点播** 规划，并保留清理、注册、录像和其他业务余量。
- 若需要达到 250～300 路，先把压测工具、WVP、ZLM、Redis 和观看/解码端拆到独立主机，再使用真实目标码率做至少 30 分钟稳态和重复启停测试。
- 300 路区间应重点补齐 HTTP 失败响应体、WVP 请求耗时/线程池、Redis 命令延迟、数据库连接池、ZLM RTP/协议连接数和网络丢包指标；否则只能知道“失败”，不能定位容量瓶颈。
- 在 WVP 控制面恢复并确认旧会话完全排空前，不应直接复用本轮环境继续加压；恢复后的首轮应先做 10～25 路健康回归，再从 200、225、250、275、300 路逐级验证。

## 8. 测试边界

- 这是同机、低码率、短时、多轮生命周期测试，不是独占硬件基准，也不是精确物理上限。
- 未覆盖高码率长稳态、真实摄像头厂商差异、复杂目录规模、完整 Prometheus/数据库查询延迟、网络丢包和故障注入。
- 本轮没有重启 WVP/ZLM、手工清理 Redis/SQL、删除设备或触碰 `t.cap`；250/500 路未执行是有意的安全停止，不是漏测。
