# 压测工具缺陷修复与复测说明

## 范围与边界

本轮根据真实环境阶梯测试发现的问题修复 `tools/gb28181-load-test`，不修改 WVP/ZLM 代码、运行配置或服务状态，不覆盖原二进制，不提交 Git。既有媒体、配置、测试报告、凭据和 `t.cap` 均保留。

用户已释放磁盘空间，开始实现时实测可用约 14G。这个空间条件允许后续从单路复测开始，但不等于监控和容量验收条件已经满足。

## 修复设计

1. 媒体源按 PS 包长度解析，不在视频负载中搜索任意起始码。支持 MPEG-1/2 pack 和有界 PES，按视频 DTS（无 DTS 时使用 PTS）建立定时 PES 分组；同时间戳的后续 PES 保留在同组。时间戳支持 33 位回绕，拒绝无法确定节奏、倒退或超过 10 秒的异常时间间隔。末组使用上一组间隔，循环时推进 RTP 时间戳并重写 SCR/PTS/DTS；共享文件不被修改，每次只复制当前分组。分组不是承诺逐帧重编码，视频格式、帧边界仍由原 PS 负载保存。
2. UDP/TCP sender 使用媒体时间间隔调度；显式设置 `Interval` 时才覆盖媒体节奏。TCP 建连可取消且最长 5 秒，写入有 5 秒期限，停止关闭连接解除等待。每次 INVITE 创建独立 sender，Stop 后永久拒绝再次 Start，避免迟到 ACK 在最终清理后重新打开连接；启动登记与停止检查使用同一锁，TCP 发送循环所有退出路径都关闭本次连接。实际包数、字节数和错误每秒采集，停止时补齐；计数游标仅在安装新 sender 时重置，不重计上一条流。
3. INVITE 响应回显 CSeq，保存 URI/tag/Contact/Record-Route；ACK 必须匹配 Call-ID/CSeq，重复 ACK 不再次启动 sender。SDP 使用 INVITE 提供的 SSRC，并返回 sendonly 和正确的 TCP active 标识。BYE 使用独立本地 CSeq，按 dialog 的 Contact/路由下一跳发送；等待最终响应并有限重传，默认等待最多 3 秒。停止和关闭期间不接受新 INVITE，旧主动退出定时器不能关闭新 dialog。工作负载结束后保留接收循环，完成 BYE 确认后再关闭传输。
4. 注册设备成功率排除 Digest 挑战，真实尝试在发送前计数；Catalog、DeviceInfo、DeviceStatus 分类统计。无尝试是 N/A，不是成功或失败。点播阶段的本地 sender 启动与 WVP 响应媒体确认分开记录，并限制同一设备不重叠调度。已配置时长、零点播速率的在线专项会保持运行到时长结束。
5. 监控源分别可选，ZLM-only 可运行；资源监控缺失仍是 INCONCLUSIVE。报告在 JSON/控制台/Markdown 中明确可用性；CSV 原有列保留，新字段追加。媒体发送错误、BYE 错误/超时不会被最终零残留掩盖。
6. 清理只读检查本次设备编号、业务流和已观察到的 SSRC。默认等待 30 秒、间隔 1 秒，连续两轮流/listener/WVP 可见会话归零才算收敛。检查不可用和宽限期超时影响判定完整性，不以缺失查询结果冒充零残留。不直接检查 Redis InviteInfo/SIP 内部索引，不调用全局关闭/删除接口。

## 配置与报告变化

现有配置继续可用，新增可选配置：

```yaml
monitoring:
  enabled: true
  sampleInterval: 5s
  cleanupTimeout: 30s
  cleanupInterval: 1s
  zlm:
    enabled: true
    url: http://127.0.0.1:19001
    mediaServerId: zlmediakit-local
```

仅用 ZLM 时不再要求填写一个不可用的 Prometheus 地址；ZLM secret 保留在本机私有配置中，不写进报告。两种源均未配置时，启用监控仍会被校验拒绝。

JSON 的 `business.checks` 包含 attempted、succeeded、available、evidence。没有执行的成功率为 null，人工报告显示 N/A。Catalog 是设备响应发送证据，停止是接口成功证据，不能分别等同于数据库持久化完成或资源全部回收。`senderAt` 与 `mediaAt` 分别对应本地发送器和 WVP 返回匹配业务流；后者不是独立持续拉取播放器的播放质量证据。

每台设备的明细增加 RTP 实际计数以及 BYE 成功/错误/超时；CSV 从 27 列扩展为 39 列，前 27 列顺序不变，需按表头读取。`mediaAt` 和 `mediaConfirmationLatencySeconds` 的含义已纠正，旧版本将其误用为本地 sender 启动，不应直接比较两版该指标。

清理报告增加残留 listener、WVP 可见会话、各检查可用性、是否按测试范围过滤、等待时长和超时标记。即使全零快照可用，宽限期内没有完成收敛确认也不能判 PASS。

## 本地验证与媒体校准

先通过回归测试复现整文件发送、时钟归零、固定 40ms、CSeq 不匹配、错误 BYE、未确认 BYE、旧会话定时器、统计混算、ZLM-only 校验、过早残留快照等问题，再修改对应实现。最终需运行：

```bash
cd tools/gb28181-load-test
go test ./... -count=1
go test -race ./... -count=1
go vet ./...
GB28181_TEST_MEDIA="$PWD/media/sample.ps" \
  go test ./internal/rtp -run TestPreparedMediaTimeline -v -count=1
go build -o bin/gb28181-load-test-candidate-20261011 ./cmd/gb28181-load-test
```

媒体校准测试只读取本机文件并解析时间轴，不访问 WVP/ZLM。现有 sample.ps 实测：845824 字节、395 个定时 PES 分组、30 秒，PS 负载平均约 0.226Mbps。这不是典型 2–8Mbps 高清摄像头的码率；后续要测试网络/录像容量，应使用接近实际业务码率的视频，并保留原文件。

候选二进制单独生成。复测时可通过 `GB28181_LOADTEST_BIN` 指定候选文件，无需替换现有二进制。

## 后续真实环境复测项目与风险

用户随后授权并完成四个单路阶段，实际步骤、证据及新发现的问题见 [候选压测工具单路复测记录](2026-10-11-候选压测工具单路复测记录.md)。信令和资源回收路径通过，但真实 RTSP 时间轴及现场清理接口响应适配仍有缺陷，当前不能进入容量验收。

本轮实现不自动进行真实环境加压，统一留待后续安排：

| 阶段 | 测试项目 | 核查证据与风险 |
| --- | --- | --- |
| 准备 | 服务/磁盘/监控与独占测试编号段 | 重新检查可用空间、录像策略、Prometheus、运行 WVP 构建；不得复用正在使用的生产编号/测试编号 |
| 单路短时 | REGISTER、Catalog、INVITE、ACK、TCP/UDP RTP | CSeq/SSRC 严格匹配、正常码率、画面可播放；自动截图和录像也会耗用空间 |
| 单路重复 | HTTP 停止、无人观看关闭、再次点播 | 两次会话不串扰；BYE 200，Hook、listener、可见 SIP session 收敛；检查清理等待报告 |
| 主动退出 | device-bye、运行时间结束、SIGTERM | 最终 BYE 成功/拒绝/超时明确显示，无残留；等待上限不等于未经测量的真实网络清理耗时 |
| 信令阶梯 | 10/50/100 台在线专项、续订与心跳 | playRate=0，无媒体落盘；N/A 不用于确认点播容量，设备/通道数据库记录可能保留 |
| 媒体阶梯 | 从少量并发递增，每档观察资源和码率 | 保持观看端或明确无人观看策略；设置磁盘/CPU/延迟/失败率停止条件，不能仅凭 14G 空间跳到高并发 |
| 故障注入 | 无媒体、不可用 TCP 端口、监控不可用 | 不套用正常媒体容量阈值；实际错误、N/A、查询失败必须可见 |

WVP `/api/play/ssrc` 是公开 API 可见的会话检查，不是 Redis 所有内部记录的完整验收；需另行安排 Redis 索引核验。设备退出后数据库记录不删除，在线状态可能等待 REGISTER/心跳到期。Prometheus 不可用时无法确认 CPU/JVM/Redis/MySQL 等资源瓶颈，更不能据 ZLM 单项判定容量极限。
