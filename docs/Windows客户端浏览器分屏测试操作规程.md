# Windows 客户端浏览器分屏测试操作规程

版本：V1（2026-10-14）。状态：流程已整理，当前 Windows 客户端尚未执行视频容量测试。

## 1. 目标与边界

- WVP、ZLM 和模拟设备仍运行在服务器；Windows 电脑只运行 Chrome 并访问真实分屏页面。
- 先测实际使用配置的可用分屏数，再按需安排内存硬限制、高清素材或其他播放器的独立实验。
- 不需要在客户端安装 Java、Redis、ZLM 或模拟器，不需要为本测试重启服务。
- 本规程的人工观察用于初筛；只有逐路渲染、帧率、延迟采样齐全时，才能声称通过量化流畅度验收。
- 最大实测通过档位不等于最大容量；9 路全部通过时，原生界面只能证明“至少支持本次验证的 9 路”。

## 3. 固定测试条件

每台电脑均记录并尽量固定以下条件：

1. 同一服务器及前后端版本、同一播放器和解码配置。
2. 同一素材集合，记录编码、分辨率、帧率、码率、音频与素材校验值。
3. 同一分屏档位、浏览器缩放 100%、相同窗口尺寸或明确记录差异，页面保持前台可见。
4. 同一网络接入方式，避免其他大下载、视频会议等可变负载；不关闭安全软件来追求成绩。
5. 记录 Chrome 版本、扩展、图形状态、Windows 版本及云桌面连接方式，差异不能隐藏。

基础素材可沿用服务器轮的 `tools/gb28181-load-test/media/sample-v2.ps`：
H.264 High、640x360、25 fps、约 209 kb/s、无音频、30 秒循环。
此项仅作为流程和跨机对照基线；另用符合真实摄像头参数的素材验收业务容量。

当前已测部署默认使用 Jessibuca，`useMSE=false`、`useWCS=false`、
`forceNoOffscreen=true`。换播放器、改配置必须另测，不能把 WebRTC 的结果记到 Jessibuca 名下。
Chrome 声称支持视频硬解也不能单独证明 Jessibuca 正在使用硬解。

## 4. 服务端准备（由维护者执行）

- 测试前只读核验 WVP 健康、既有会话、媒体节点和服务器资源，保留基线。
- 上一轮模拟流已经停止；需在约定测试时段启动新的专用模拟设备，不复用已用编号段而不检查冲突。
- 模拟设备独立注册、点播和发送 RTP，每个分屏使用独立通道及播放器；记录测试设备、通道和 Invite 身份。
- 如果改用同一摄像头的多个播放器，只能标为“同源多实例”，不能冒充独立摄像头端到端负载。
- 用正常登录账户进入“分屏监控”；先验证单路。页面可访问不等于 WS-FLV 等媒体地址和端口可从客户端访问。
- 模拟器必须在每档结束后仍可继续提供素材，或由维护者重启该档专用源；不要假定关闭观看窗口后上游一定继续推流。
- 初次只测原生 1/4/6/9 分屏。超过 9 路需另行准备测试入口，当前规程不修改或部署生产前端。
- 风险：增加 ZLM 出网、服务端会话及客户端 CPU/内存负载；仅停止本次测试对象，不影响既有业务流。

## 5. Windows 电脑操作步骤

1. 保存正在编辑的工作，关闭无关标签页；保留正常安全软件和日常必要应用，记录残余负载。
2. 推荐使用不启用同步的专用 Chrome 测试配置文件，不删除或覆盖日常配置。换电脑仍沿用同样的扩展策略。
3. 打开 `chrome://version` 和 `chrome://gpu` 保存环境截图，然后关闭这些标签页。
4. 在 Windows 任务管理器记录实际逻辑处理器数、CPU、可用内存、Chrome 内存和网络空闲基线，观察 2 分钟。
5. 用正常登录方式进入服务器“分屏监控”，首次确认单路连通；不要对外开放 Chrome 远程调试端口。
6. 每档使用干净页面：停止上一档测试播放并刷新页面，确认无残留观看连接，再加载本档全部测试视频。
7. 最后一路出画面后预热 60 秒，再按下表计时。保持页面前台，不最小化，不让电脑休眠。
8. 每分钟记一次资源值；发生异常立即记时间、路数和现象，保存截图。每两分钟点击选择不同窗口并操作非破坏性菜单。
9. 观察完停止本档测试播放，观察 2 分钟回收趋势。允许缓存保留，不要求内存必须回到完全相同数值。
10. 确认观看连接已释放、上游可用后进入下一档；一次资源未回收不能直接定性泄漏，需要重复开关后的趋势证据。

| 档位 | 正式观察时间（不含预热） | 用途 |
| --- | --- | --- |
| 1 路 | 5 分钟 | 连通和单路性能基线 |
| 4 路 | 10 分钟 | 首个多路档 |
| 6 路 | 10 分钟 | 中档 |
| 9 路 | 10 分钟 | 原生界面最高档 |
| 最后一个初筛通过档 | 每轮 30 分钟，共 3 个独立轮次 | 稳态候选验证，不代表数小时或全天稳定 |

首个失败档不继续加压，退回上一通过档独立复验。
如果 1 路通过而 4 路失败，2/3 路仍属未测区间；可在 4 格布局中只加载 2/3 路补测，记录实际播放路数。
换电脑时重复完整流程，不能直接从上一台电脑的最高档开始。

## 6. 监测与判定口径

### 人工初筛

- Chrome `Shift+Esc` 用于定位页面、GPU/Worker 等进程；Windows 任务管理器观察 Chrome 整组资源和系统资源。
- 明确记录内存列名与单位，例如“活动专用工作集”；不同 Windows/Chrome 内存口径不能混算，也不能直接与容器 cgroup 总内存比较。
- 浏览器整组占用应包含本轮 Chrome 的相关子进程；包含其他配置文件或遗漏 GPU/utility 进程时注明统计不完整。
- 记录 CPU 总占用和各逻辑处理器状态。GPU 数值不可用时填“不可用”，不能填 0 当作实测。
- 初筛通过：所有窗口持续出画面，无肉眼可见连续超过 2 秒冻结、无黑屏、无崩溃或持续重连，交互无明显卡死。
- 肉眼观察不能证明每路达到 20/25 fps，也不能证明不存在短时丢帧。没有仪器采样时，结果必须标“人工初筛通过”。

### 后续量化验收（采样工具接入后执行，不宣称目前已经具备客户端采样）

- 复用真实页面播放器，逐路采集 stats、PTS、有效 canvas draw、context lost、错误以及事件循环延迟。
- 不能只查视频连接数、播放事件或 `<video>` 元素，Jessibuca 画布失效时仍可能保持网络连接及解码 stats。
- 对上述 25 fps 基础素材，可沿用服务器轮标准：预热后每路所采 stats 不低于 20 fps、渲染/PTS 更新年龄小于 3 秒、
  无 context lost 或错误，事件循环延迟 P95 小于 250 ms，采样命令响应小于 2 秒；同时报告实际 draw 速率分布。
- 不同帧率的业务素材应在执行前定义其阈值，不能测试失败后降低标准再宣称通过。
- 使用先前服务器探针前要适配并验证 Windows 桌面 Chrome 的采样和进程归属，不能直接把 Linux 容器脚本当成已可用的 Windows 工具。

### 安全停止线

- 页面崩溃、系统交互明显失灵、持续黑屏，立即停止增加路数并关闭本次测试页。
- CPU 总占用持续超过 85% 达 60 秒，或系统可用内存低于 2 GiB，停止升压并降档；记录为安全停止，不冒充找到绝对容量。
- WVP 健康异常、服务端安全线触发或影响既有业务时停止测试，由维护者仅清理本次资源。
- 不为了寻找极限故意耗尽系统内存；不压低 WVP/ZLM 预算，不修改虚拟内存，不禁用安全软件。

## 7. 内存受限测试单独安排

本轮“总内存约 20 GB、可用约 10 GB”只是电脑环境描述，不是浏览器 10 GB 或 4 GiB 硬限额。
`--max-old-space-size`、JS heap 指标、单 renderer 内存或关闭其他应用都不能替代整个浏览器进程组硬限制。

如后续要求严格 4 GiB，需独立设计、验证包含子进程的 Windows 进程组限制，或在受限虚拟机中运行。
虚拟机 4 GiB 是整台来宾系统预算，且可能改变 GPU 路径，不能伪称与服务器浏览器 cgroup 4 GiB 完全等价。
实际客户端容量与内存限制容量分别报告。

## 9. 收尾与待执行验收

- 客户端停止本次全部播放并关闭测试页，检查本轮 Chrome 进程和资源变化，不终止其他用户进程。
- 服务端按测试身份退出模拟器，核验 Invite 终态、活跃索引、SSRC、SIP 会话、ZLM 媒体及观看连接。
- 不删除真实设备或清空 Redis/SQL；是否保留模拟设备元数据明确记录。
- 核验 WVP 健康和服务器资源回到合理基线；保存结果和异常，未测区间保持“未知”。
