# Invite 生命周期并发故障根因与统一改造方案

## 1. 结论与本次边界

本次问题不是单纯的删除重试次数不足，也不是媒体发送能力不足。已确认的故障链是：

```text
不同设备同时创建/更新 Invite
  -> WATCH 同一个主 Hash，相互使事务失效
  -> EXEC 中止被客户端转为空 List
  -> 代码只判断 null，将未提交当作成功
  -> void 写接口无法向业务传递真实结果，继续发 INVITE
  -> SIP/RTP/媒体已经存在，Invite 主记录却缺失或仍未完成
  -> 成功回调丢失，或先写入数据库播放标记但 Redis 更新失败
  -> 部分退出路径只删元数据，数据库播放标记没有可靠收尾
```

此前原子删除改造解决了删除动作的共享 Hash WATCH 冲突，未解决创建、更新和完整生命周期一致性。本次不能再以增加重试、激活 ready 标记、延长客户端超时作为最终修复。

本文最初为根因分析及待实施设计。用户随后确认实施，当前源码改造和验证边界见 [Invite生命周期统一改造实施与验收](2026-10-11-Invite生命周期统一改造实施与验收.md)。本文中的真实环境证据来自改造前，不代表新协议已经部署或通过真实环境验收；本轮仍不改运行 Redis/数据库、不部署、不重启、不提交 Git。

## 2. 已确认根因与证据

### 2.1 不同设备的事务被错误地耦合

`InviteStreamServiceImpl.watchInviteMutation()` 在索引未 ready 时，除目标版本 key 外，还 WATCH `VMP_GB_INVITE_INFO` 整个 Hash。运行标记为 backfilled，不等于 ready，所以实际走这条路径。Redis WATCH 的粒度是 key，不是 Hash field；另一个设备修改任意 field，也会让当前事务中止。

已有真实环境复验中，17:20:27 同时重新点播 10 路：

| 项目 | 已观察结果 |
|---|---|
| 10 次 ready 创建事务 | 4 次提交、6 次中止 |
| 包含后续更新的事务中止 | 共 11 次 |
| 新 RTP resourceId、媒体和 SIP | 10 路出现 |
| 业务点播成功回调 | 只有 4 路 |
| 后续更新读取不到 Invite 的日志 | 6 台设备 |

证据：`tools/gb28181-load-test/reports/media-stair-20261011/invite-retest-atomic-api-replay.failure-evidence.json` 及同前缀 `.redis-wire.jsonl`、`.wvp-log.jsonl`。

### 2.2 EXEC 中止被当作成功

创建路径使用 `operations.exec() == null ? null : true`；其他更新、恢复、索引维护路径也有相同或未校验提交结果的用法。实际依赖栈会将 Redis 的中止结果转换为空 List，因此不会进入预期的冲突重试。

已有隔离验证使用实际 Lettuce 和 GenericFastJsonRedisSerializer，两个独立连接修改同一 Hash 的不同 field，输出：

```text
EXEC_IS_NULL=false
EXEC_LIST_SIZE=0
TARGET_UNCHANGED=true
CURRENT_CODE_WOULD_REPORT_SUCCESS=true
```

验证源码为上述报告目录内 `RedisExecResultProbe.java`，输出为 `target/invite-atomic-check/exec-abort-probe.log`。该验证使用隔离 Redis，不是运行环境故障注入。

### 2.3 写入接口不能表达失败，副作用继续执行

`IInviteStreamService.updateInviteInfo()` 两个重载都返回 void。`PlayServiceImpl.play()` 写 ready 后直接调用 `cmder.playStreamCmd()`，无法要求“确认持久化成功后才能发 INVITE”。SIP 200 OK 的更新也存在同类问题。

媒体回调发现主记录缺失时，owner 判断把它与“已被新 owner 替代”一起处理，直接忽略。前者是当前会话建立失败，需要失败回调和自身资源回收；后者才是不得操作新会话，两者不能混为一谈。

`RtpResourceContext.completeSuccess()` 在调用业务回调前已进入 SUCCESS；业务持久化失败不会因为后续重复媒体 Hook 自动重跑完整成功流程。不能依赖再来一个 Hook 自愈。

### 2.4 数据库播放标记先写，且没有 owner 约束

`PlayServiceImpl.onPublishHandlerForPlay()` 先执行 `deviceChannelService.startPlay()`，再更新 InviteInfo，最后仍返回 StreamInfo。Redis 更新未确认，数据库却可能已经显示播放中，API 也可能报告成功。

`DeviceChannelMapper.startPlay()` 和 `stopPlayById()` 都只按通道 id 更新，没有 inviteId 或代次条件。即使把 Redis 更新简单挪到 SQL 之前，也不能解决跨线程、跨系统的旧 start/stop 竞态；同一设备的下一轮 streamId 还可能与上一轮相同，按 streamId 判断也不充分。

### 2.5 退出路径未统一收尾

- `processInviteExpiry()` 对未完成 Invite 调用元数据删除，不保证 BYE、SIP、RTP 和数据库状态清理。
- `DeviceServiceImpl.cleanOfflineDevice()` 分别关闭资源、删 SIP，再调用 `clearActiveInviteInfoByDeviceId()` 删除 Invite；不是一条可恢复、可确认的完整停止流程。
- `PlayServiceImpl` 媒体离开处理要求 status=ok 且 streamInfo 非空，缺失或未完成的会话会被跳过。
- 现有完整清理待办依赖先找到 Invite 快照，无法覆盖“资源已创建但主记录从未成功写入”的窗口。

最终只读检查已发现通道 309、311 状态为 OFF，但 streamId 非空，而媒体、listener、SIP、Invite 主记录均为零。这是确实存在的业务状态残留。由于第二阶段采集提前结束，不能确定两个通道各自最终经哪条删除路径消失；源码证明这些路径存在缺口，但不将推断当作完整现场证据。

### 2.6 一并消除的相关设计风险

以下有源码依据，但不作为本次现场故障的已证实直接原因：

- ready 更新可以覆盖已有记录；创建和更新没有严格分离。
- owner 依赖可选 resourceId，缺失时退化为对象相等判断。
- `InviteSessionStatus` 仅 ready/ok，ok 同时用于 SIP 接受和媒体就绪，难以防止乱序更新及错误清理判断。
- 回调按 type/channel/stream 注册，不按本轮 Invite 身份隔离；遍历后 remove 存在并发注册丢失窗口，异常也会中断其他回调。
- 查询在索引异常时回退扫描；存储失败、记录缺失和索引未就绪容易混为业务“没有会话”。
- 旧清理任务发现新 owner 就整体退出，可能不再回收旧 owner 的独占资源；仅凭业务流名又无法安全区分两代资源。

## 3. 目标与不变量

采用一套 Invite 生命周期协议，不保留旧/新存储并行、双写、回填兼容、旧 Hash 扫描兜底或恢复旧快照模式。沿用现有 HTTP 业务入口和 GB28181 协议，不以破坏设备协议作为解决办法。

必须成立的不变量：

1. 一轮操作先有不可变 inviteId，再有外部资源；inviteId 不因 SSRC、流名或 resourceId 变化而改变。
2. 同一业务槽位只能有一个当前 owner；并发重复请求加入该 owner，不能重复创建 listener/发送 INVITE。回放、下载按实际可并行的任务定义槽位，不能简单按 channel 全部互斥。
3. 未确认创建记录及资源绑定，不发送 INVITE；存储不可用是明确失败/结果未知，不是“未找到”。
4. SIP 接受、媒体到达、数据库投影确认分别记录。只有本轮成功条件全部提交后才能完成成功回调。
5. STOPPING 后不再接受成功迁移；过期回调不得复活会话、覆盖新 owner 或清空新播放状态。
6. 非终态会话不能直接删除。API 停止、设备 BYE、媒体离开、超时、离线和异常均进入完整清理流程。
7. 主记录、owner 指针、索引、到期集合和清理阶段由统一存储层维护，不允许业务自行拼 Redis key 写入。

## 4. 统一存储与状态协议

### 4.1 分层和数据模型

- `InviteRepository`：唯一存储写入口，负责 Lua、索引、revision、幂等结果和查询错误分类。
- `InviteLifecycleService`：唯一编排入口，协调创建、SIP/媒体事件、成功确认和停止。
- `InviteCleanupWorker`：执行已持久化清理意图，记录独立步骤确认，负责失败重试及对账。

新记录至少包含 inviteId、业务槽位、serverId、device/channel/type、revision、deadline、生命周期状态、SIP/媒体事实、精确资源绑定及清理进度。resourceId、SSRC、Call-ID 是资源关联信息，不能代替 Invite 的业务身份。

使用独立 namespace、按 inviteId 存主记录；owner 指针及设备/通道/媒体/SSRC/Call-ID 索引指向 inviteId。流名修改仅修改关联索引，不改变主键。活动记录不靠 Redis TTL 自动消失，到期集合驱动完整关闭；终态摘要和已完成下载结果才按明确保留策略过期。

现有环境按 Redis 单机/Sentinel 设计和验收；不宣称自动支持 Redis Cluster，多 key Lua 不满足同 slot 时启动即明确拒绝，不运行到中途才退化为旧实现。

### 4.2 原子命令与结果契约

至少提供 `createAndClaim`、`bindResources`、`recordSipAccepted`、`recordMediaArrival`、`activate`、`beginStop`、`ackCleanupStep`、`finishClose`。禁止通用的“整对象覆盖更新”和 update-as-create。

Lua 校验 inviteId、revision、状态和精确资源身份，在单次执行内维护主记录及派生数据，不再 WATCH 全局 Hash。不同设备不会因无关 field 更新产生乐观事务中止；Redis 本身仍顺序执行命令，不宣称无限并行。

存储结果显式区分 APPLIED、ALREADY_APPLIED、OWNER_CHANGED、STATE_CONFLICT、NOT_FOUND 和技术失败。网络超时另标记 COMMIT_UNKNOWN，通过 inviteId/操作标识读取确认；不能将未知直接当作失败后重建，也不能直接当作成功。重试同一操作必须幂等，更新不存在的主记录必须失败。

脚本只做固定上界的数据操作；写前检查参数和 key 类型。Lua 原子执行不等于异常回滚，仍须对部分写入异常告警和对账。Redis 持久化、内存策略和不可恢复数据丢失属于基础设施保证范围，不以“用了 Lua”掩盖。

删除 ready/backfilled/activate/backfill 分支、主 Hash 业务查询回退、restoreIfAbsent 和旧协议写入口。所有调用点一次性切换；接口保留也只能委托新编排，不能保留旧行为。

### 4.3 明确状态和乱序事件

```text
PREPARING -> WAITING_MEDIA -> ACTIVATING -> ACTIVE
     |             |              |          |
     +-------------+--------------+----------+-> STOPPING -> CLOSED
```

SIP_ACCEPTED 与 MEDIA_ARRIVED 是独立事实，允许任意先后顺序，不用一个 ok 表示两件事。二者齐备才尝试 ACTIVATING，完成需要的数据库投影并确认 Redis ACTIVE 后，才完成成功回调。失败原因单独记录；失败会话仍须完成 STOPPING，不绕过清理直接消失。

下载完成后先关闭活动 SIP/RTP 资源，再按既定时间保留下载结果；“结果仍可查询”与“资源仍活动”不是同一状态。

## 5. 创建、回调与媒体身份

执行顺序固定为：

1. 生成 inviteId，持久化 PREPARING 并原子认领业务槽位。已有 owner 时加入等待，STOPPING 时等待关闭或返回明确可重试结果。
2. 完成必要的数据库 owner 预留，持久化计划中的精确 RTP 目标，然后调用 ZLM；确认实际 listener/SSRC/resourceId 绑定。创建返回未知时按精确目标查询，不盲目再开一个。
3. Call-ID 和 SIP 发送意图持久化后才发 INVITE；会话管理器关联同一 inviteId。收到 SIP/媒体事件分别提交事实，失败或未知进入确认/补偿，而不是报告成功。
4. 完成 ACTIVE 提交后，按 inviteId 完成对应请求；截图等非必要动作移出成功关键路径。

实际发布媒体流名按代唯一，原 device/channel 组合只作为逻辑业务标识；播放 URL 使用本轮实际流名。listener 和发布流均以精确节点/app/流身份操作，不再以共享业务名猜测关闭目标。相关 Hook、MediaStreamUtil、API、级联及压测工具的流名解析须改为显式元数据关联，不能只改 ZLM 的 stream_replace 一处。

该要求解决旧 HTTP 关闭请求或无 originUrl 的延迟注销 Hook 误击新一轮同名流的问题。缺失可靠来源的 Hook 必须查询精确媒体状态，探测失败是未知，不等同已离开；不能看到某个 stream 字符串就停止当前 owner。

回调注册表按 inviteId 隔离，注册与完成采用同一个原子协调协议：完成时摘除等待者并保存终态，晚注册者读取终态，不能 get/遍历/remove。每个等待者独立超时和异常隔离；旧请求取消不应取消新 owner，单个观看请求超时是否停止共享会话须按业务等待者规则处理。

## 6. 数据库播放投影的代次栅栏

仅交换 Redis/SQL 顺序或增加 `WHERE stream_id=?` 不够。必须使旧代 start 和 stop 都失去写新状态的权限。

实时点播投影在通道记录增加以下概念字段，具体 SQL 迁移需覆盖项目支持的数据库：

- `play_generation_seq`：数据库持久化递增的代次分配计数。
- `play_owner_epoch`、`play_owner_id`：已应用投影的代次和 inviteId。
- `play_owner_state`：PREPARING、PLAYING、CLOSED；停止后保留代次水位，不清空 owner 历史水位。

分配计数和已应用代次分开：竞争失败者可以消耗编号，但不能因此使正在播放的胜出 owner 失效。业务认领成功且数据库预留成功前，不创建外部资源。

SQL 约束：

1. 新 owner 预留仅能推进到更大 epoch；同 owner 重试只能确认已有 PREPARING，不能把同代 CLOSED 改回 PREPARING。
2. start 必须匹配 ownerId/epoch 且处于 PREPARING；相同 PLAYING/stream 的重试读回确认，其他情况不得当成功。
3. stop 将本代状态置 CLOSED、清空 streamId，并保留水位。清理可能发生在预留尚未提交之前，因此已成功认领的 owner 关闭时还须推进低代水位至本代 CLOSED，阻止迟到预留；认领失败者没有此权限。
4. 低代 start/stop/预留都不能修改高代投影。SQL 影响行数为零须区分幂等、被新代替换及真实异常，禁止 void 无条件更新。

这样即使新一轮已经开始又结束，旧 start 也无法复活旧播放标记。当前涉及播放投影的所有写点必须接入，不能留下无 owner 的 mapper 路径。

Redis、SQL、SIP 和 ZLM 不构成跨系统事务。中间阶段必须可查询、可恢复：数据库写成 PLAYING 而 Redis ACTIVE 尚未确认时，由待处理阶段继续确认或安全停止；不得永久留下只有数据库“在播放”的记录。

## 7. 统一停止、恢复与对账

停止先原子进入 STOPPING 并保存清理意图/精确绑定，不先删主记录。分步骤确认 SIP 结束、SIP 索引删除、RTP/listener/发布流关闭、SSRC 释放和数据库投影清除，最后关闭并释放业务槽位。

API 停止、设备 BYE、离线、失败、超时、媒体离开、下载结束、人工管理接口都调用该流程。设备 BYE 不反向重复发送同一 BYE；其他业务根据 SIP 阶段执行对应终止动作。重复 stop 是幂等确认，不是重建 Invite。

旧 owner 被替换时，仅跳过它无权操作的共享指针/新投影，仍回收旧 owner 独占的 Call-ID、resourceId 和按代唯一流，不能整体丢弃旧任务。无法确认精确资源已关闭时保留未知状态，不把底层 false 一律当成功。

未完成待办不设 TTL，独立有界 worker 按预算执行、退避重试并报告最老任务年龄。操作租约只用于调度互斥，真正权限由 inviteId/epoch/resourceId 决定，不能把“租约未过期”当跨系统锁。

启动及周期对账按索引/分页推进，覆盖 PREPARING、ACTIVATING、STOPPING、精确媒体资源和数据库播放投影。读取失败不得解释成资源不存在；不在业务请求中全量扫描。记录无副作用的“计划目标”能覆盖 listener 创建后绑定响应丢失或进程退出窗口。

## 8. 一次性切换，不做存储兼容

1. 停止接受新点播，使用当前流程排空活动会话和未完成清理；核实媒体、SIP、数据库播放状态，不仅检查 Invite 数量。
2. 对旧 namespace、未完成待办和仍有效下载结果做受控留档。无法排空的任务必须先处理，不允许忽略后直接清库。
3. 备份后执行数据库字段迁移，部署新代码，使用新的空 Invite namespace；不自动读取、回填或双写旧数据。
4. 对已发现 309、311 残留，仅在核实无对应真实会话后安排受控修复；本轮不手工清除证据，也不启动时无条件清空所有通道 streamId。
5. 验收新协议后，按明确 key 清单另行清理旧数据，禁止 FLUSHDB。回滚同样要求排空，不承诺旧版本直接读取新会话。

没有新旧节点混跑，不需要保留索引兼容开关。下载结果留档及停机切换的影响须在实际部署前明确告知。

## 9. 实施顺序及覆盖清单

| 顺序 | 工作 | 完成门槛 |
|---|---|---|
| 1 | 固化实际依赖栈的并发失败回归，整理全部 Invite/投影写点 | 测试能揭示静默成功、旧 start/stop 和未完成清理 |
| 2 | 新模型、原子 Repository、唯一索引及显式错误契约 | 无全局 WATCH、无兼容分支、无写后未知吞掉 |
| 3 | 创建、SIP/媒体事实、owner 等待者和成功确认编排 | 未落盘不发 INVITE；同槽位只有一个资源 owner |
| 4 | 代次投影迁移、按代媒体身份和所有调用方接入 | 旧 SQL/Hook/HTTP 关闭不能改新会话 |
| 5 | 统一停止、持久化阶段恢复及分页对账 | 所有非终态退出均完整收尾，不只删 Invite |
| 6 | 删除旧 API/任务分支，执行离线及真实环境验收 | 无遗漏旧写点、无新旧数据双轨 |

覆盖范围至少包括：PlayServiceImpl 的实时/回放/下载/对讲广播，PlatformServiceImpl 级联/广播，ABL 下载结果更新，设备离线/删除，ByeRequestProcessor，两个媒体离开监听器，ApiStreamController 手动停止，测试/诊断控制器，Invite 索引回填和到期任务，清理待办存储，SIP 会话关联及全部数据库播放标记写点。对讲/级联按资源实际拥有方处理，不强制伪造接收 RTP resourceId。

## 10. 验证、真实环境计划与风险

### 离线及隔离验证

- 用实际序列化器/Lettuce/Lua 执行至少 100 个不同设备并发创建、更新和删除，并持续产生无关写；主记录、索引、到期集合及返回结果一致。
- 同一通道 100 个并发请求只产生一个 owner、listener 和 INVITE，每个等待者收到正确本轮结果。
- 覆盖 SIP/媒体乱序、重复事件、初始存储失败、提交成功但响应丢失、数据库失败、每个阶段进程退出及恢复。
- 明确延迟旧代预留/start/stop，验证新代停止后旧代仍不能复活状态；STOPPING 不接受 ACTIVE。
- 覆盖无 originUrl 的旧 Hook、旧媒体关闭响应迟到、新 owner 接管、清理租约到期及旧任务独占资源回收。
- ready、缺少媒体信息、外部创建结果未知、设备离线及下载保留到期均完整收尾；读取错误不能变成 NOT_FOUND。
- Lua 错误、索引异常、记录丢失和对账预算受控；任何未知不以资源归零或待办为空冒充成功。

### 集中安排的真实环境验收

真实环境写测试和故障注入不在本轮执行，后续需按以下顺序集中安排，先验证正确性再加压：

| 阶段 | 步骤 | 风险与通过条件 |
|---|---|---|
| 10 路完整闭环 | 新模拟设备注册，10 路同时开始，首末两路解码 40 秒；保持设备在线并发停止、重复停止，再同时重新开始并重复解码/停止 | 每个 API 请求有独立结果；所有业务/媒体/DB 状态收敛；退出后继续观察至少 70 秒 |
| 25/50 路 | 10 路完整通过后逐级增加并发，重复同一闭环 | 禁止上一阶段有残留仍升压；监控磁盘、CPU、内存、GC、调度及待办积压 |
| 隔离故障环境 | 分阶段重启、Redis/DB/ZLM 断连和响应丢失 | 不在共享真实环境直接断服务；恢复后无跨代误删、无永久投影残留 |
| 重复与迟到事件 | 连续点播/停止同一设备，重放受控旧代事件 | 必须同时检查 API、数据库、SIP、listener 和发布流，不能只看媒体总量 |

测试客户端超时与服务端播放超时及余量对齐，单请求失败后继续保存所有请求结果，失败收尾仍采集证据。扩大客户端超时是测试可观测性修正，不算业务缺陷修复。

按 inviteId/epoch 输出阶段和失败分类，补充创建失败/未知、状态冲突、待办最老年龄、SQL owner 拒绝、对账差异及各阶段延迟指标。不记录密码、原始鉴权或完整 Redis 值。

最终成功标准是：并发请求结果正确，媒体可解码，重复停止及同设备重播正确，退出后所有活动状态和资源收敛，旧代事件无权影响新代；不是“某一处删除不再报错”。
