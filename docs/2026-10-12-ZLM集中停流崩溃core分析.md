# ZLM 集中停流崩溃 core 分析

## 范围与结论

本轮接续 [50 与 100 路阶梯压测](2026-10-12-50与100路继续阶梯压测.md)。用户指出 `zlm` 会话有 core dump，并指定 `/data/shizy/GB28181/mediaServer` 下的 core；本轮仅对该会话、该目录的程序及 core 只读取证。未重启、部署、修改或删除 ZLM，未恢复压测、手工清理 Redis/SQL 或提交 Git。

**已确认：ZLM 因 SIGSEGV（信号 11）崩溃，直接原因是媒体信息查询中对空 MultiMediaSourceMuxer 调用了 isRecording(type_mp4)。** 不是仅凭连接失败推断崩溃，也不能将此次故障判定为 100 路容量极限。

更关键的是，core 中正在查询的对象为 `TSMediaSource`、schema=`ts`、app=`rtp`、stream=`gb_1dc73627741d450ca97b2e22afe74310`，与先前独立终检留下的 STOPPING Invite 完全一致。问题集中在停流后的媒体对象/事件监听器/muxer 生命周期与查询安全性，而非已观察到的 RTP 解码错误。

### 反汇编核验

`MediaSource::isRecording()` 的实际执行顺序：

1. `_listener.lock()`，对 listener shared_ptr 判空；若空则返回 false。
2. listener 非空时通过虚函数获取 `shared_ptr<MultiMediaSourceMuxer>`；结合 `MediaSourceEvent` 虚函数表布局确认是 `getMuxer()`。
3. 对返回的 muxer **没有判空**，直接 `operator->()` 后调用 `MultiMediaSourceMuxer::isRecording()`。
4. core 中该调用的 muxer `this=0x0`，type=`type_mp4`。
5. MP4 分支取 `this + 0x2b0` 处的 shared_ptr 做布尔判断，因此访问低地址 `0x2b0` 触发 SIGSEGV。

这证明“listener 仍存在但 getMuxer 返回空”的组合确实发生，且当前二进制没有保护该组合；不是仅基于可能存在并发竞态的推测。空 muxer 如何形成、是否还存在跨线程读写竞态，需要对应版本源码和回归测试继续确认。

### 崩溃前 API 异常

终端滚屏中，同一流在关闭/查询阶段出现：

- `getOwnerPoller failed`，分别涉及 RTSP/HLS 媒体对象。
- `getMediaList` 返回 code=-400，消息 `mediakit::TSMediaSourceMuxer::totalReaderCount not implemented`。
- 14:48:22.248 的 `listRtpServer` 返回 code=0，没有 data。
- 14:48:22.251 的 scoped `getMediaList` 对该流返回上述 code=-400，随后打印崩溃栈。

相邻的已返回请求不能单独证明就是发生崩溃的那个请求。HTTP handler 和媒体对象身份由 core 进一步核验；具体崩溃请求路径另从 parser 的 URL 路径提取，不读取查询参数或正文。

最后从 core 的 `Parser._url`（去掉查询参数）与 `_method` 提取到：**`POST /index/api/getMediaList`**。因此已确定具体崩溃接口，而不是笼统的“某个 HTTP 请求”。

## 与 WVP 和压测工具的关系

- WVP 的 `closeInviteRtp()` 关闭原代 RTP listener/媒体后，调用 `listRtpServer()` 和 `probeStream()` 确认消失。`probeStream()` 底层使用 scoped `getMediaList()`；失败/异常返回 null，不会当成“已关闭”。
- 压测监控也使用 `getMediaList()`，但 Go 监控和本轮现场 Python 探针使用 GET；WVP 的 `ZLMRESTfulUtils.getMediaList()` 使用 POST。core 中的 POST 排除了工具 GET 采样请求直接触发这次崩溃，符合 WVP 的查询链路；尚未确认是 WVP 清理探测、SSRC 对账还是其他内部调用。停流、业务确认和监控查询并发是现场条件，不能将全部并发查询都当作最终崩溃请求。
- 标准媒体查询不应导致 native 进程崩溃；减少查询、关闭监控或不做清理确认都不能算根因修复。WVP 查询的并发量和节流仍可另行评估，但不能代替 ZLM 生命周期安全修复。
- ZLM 退出后，WVP 无法确认该流消失，所以保留一个 RTP 清理待办和 SSRC lease，与此前 BYE=1、SIP=1、STATE=1、RTP 未完成的事实相符。ZLM 修复与 WVP 节点失联关闭确认是两个问题，应分别验收。
- 已确认的直接原因是空指针访问，不是 OOM kill、断言终止或性能上限。现有证据不能排除其他潜在缺陷，也不能仅凭低 CPU/内存判断完整容量。

本轮仅分析，不修改产品。后续应先确认 `5f11d3b` 对应源码和本地补丁，不能只凭 master 标签或构建时间直接更换版本：

### 根因已从空指针追到代理链生命周期

关键位置（相对 `/data/shizy/ZLMediaKit`）：

| 位置 | 实际逻辑与风险 |
|---|---|
| `src/Common/MultiMediaSourceMuxer.cpp:263` | `_ts->setListener(self)`，TS 代理委派给总 muxer |
| `src/TS/TSMediaSourceMuxer.h:37` | `setDelegate(listener)`，TS media source 的 listener 设为 TS muxer 自身 |
| `src/Common/MediaSource.h:366` | interceptor 的内层 delegate 是 weak_ptr，不保证总 muxer 存活 |
| `src/Common/MediaSource.cpp:817` | 内层 weak_ptr lock 失败后调用基类 `getMuxer()` |
| `src/Common/MediaSource.h:99` | 旧版基类默认直接返回 nullptr |
| `src/Common/MediaSource.cpp:288` | 只判断外层 listener 非空，未判断 getMuxer 结果就调用 isRecording |
| `server/WebApi.cpp:452` | 每个媒体条目都查询 MP4 录像状态，即使正在列举的是 TS 条目 |
| `server/WebApi.cpp:1006` | 多条目列表在 HTTP 请求线程中生成 JSON，没有统一转移到媒体 owner poller |

对象关系是两层弱引用，不是同一个 listener：

```text
TSMediaSource
  -- weak listener --> TSMediaSourceMuxer（事件代理）
    -- weak delegate --> MultiMediaSourceMuxer（总 muxer）
```

进一步在同一个 core 中只查询相关指针与控制块，得到：

- `MediaSource::isRecording()` 的局部 listener 非空，vtable 为 `TSMediaSourceMuxer`，不是猜测其类型。
- 该 interceptor 的内层 delegate 控制块 `_M_use_count=0`、`_M_weak_count=1`，总 muxer 已没有强引用，无法 lock 成功。
- 因此走 `MediaSourceEventInterceptor::getMuxer()` 的基类回退，得到 nullptr，随后调用 `MultiMediaSourceMuxer::isRecording(this=0x0)`。该完整链与前轮反汇编、源文件逐行一致。

`MediaSource::for_each_media()` 在媒体表锁内取得的是 source 的强引用快照，随后释放锁再处理（`MediaSource.cpp:344`）。它不同时保活 source 对应的总 muxer。停流又是异步操作，释放生产端/总 muxer 时，查询可以已持有 source 和外层 TS 代理，却尚未取得内层 muxer。因此“source 存在、外层 listener lock 成功、内层 delegate 已过期”是实际可发生的生命周期窗口，不能用第一层判空排除。

本次 core 落在 `WebApi.cpp:1006` 的多条目分支；一个业务流有多种 schema 时，即使按 app/stream 过滤也会进入这个分支，不代表一定在查询多台设备。关闭操作和查询有机会运行在不同线程。尚不能从事后 core 指定释放总 muxer 的确切那一条 HTTP 请求，但其已失去强引用的结果、空返回路径和崩溃调用已确定。

`totalReaderCount not implemented` 也有一致解释：同一 interceptor 内层 delegate 过期时回退到基类 `totalReaderCount()`，基类抛 NotImplemented。它是生命周期窗口的另一种表现，不表示正常播放时 TS 不支持人数统计。

不能简单把内层 weak_ptr 改为常驻 shared_ptr：总 muxer 已强持有 `_ts`，TS 再强持有总 muxer会构成引用环，可能把崩溃变成无法释放的资源残留。查询期间取得有效强引用或使用受控异常合同才是正确边界。

### 为什么当前仍崩溃，以及修复后的边界

当前本地 HEAD/部署程序都是旧的 `5f11d3b`，在 2026-07-13 的修复合并之前。部署程序文件的 mtime 虽然是 2026-08-07，但内容 Build ID/hash 和执行逻辑仍是旧版；文件复制时间不能证明已包含新修复。

上游修复能阻止本次已确认的基类 nullptr 回退继续解引用。对本次多条目 HTTP 分支，`WebApi.cpp:307` 的任务有 `catch (std::exception&)`，NotImplemented 继承 std::runtime_error，因此会转为 API 异常响应而非 SIGSEGV。这并不承诺关闭中媒体查询永远成功；短时错误仍需调用方按“未知、继续重试”处理，不能把 code=-400 当成资源不存在。

单条目查询会再投递到 owner poller，其异步回调不应被误认为始终受外层 HTTP try/catch 覆盖。部署后的复验还要检查该分支的异常回包/超时行为。这里只确认对应崩溃入口已有上游补丁，未声称所有异步异常、共享数据或节点失联清理均彻底解决。

后续建议优先采用已合并的可追踪修复：可选择在既有版本上最小回移植 `fcdd7bd` 的两个文件改动，或升级到确认包含该提交的版本，再以实际新二进制身份和真实复验验收。不直接将整个有行尾差异的工作树 reset/pull，也不仅凭“最新包”标签验收。本轮尚未获得修改/编译/部署指令，不执行这些动作。
