# 离线设备 BYE 有界终止与复验

> 后续改造：本文保留首次有界 BYE 改造及现场复验的历史事实。随后发现 Redis/WVP 时钟偏差，因此 BYE 时间与 PENDING 调度已开展统一 Redis TIME 改造；其部署要求为先排空旧活动记录，不适用本文早期版本“直接继续处理旧 STOPPING”的上线说明。以 [BYE与清理调度统一Redis时间实施方案](2026-10-12-BYE与清理调度统一Redis时间实施方案.md) 的部署与回退边界为准。

## 根因与方案

10 月 11 日无 BYE 退出测试留下 10 条 STOPPING：RTP/STATE 已完成，BYE/SIP 未完成。原实现把对端确认作为本地释放的必要条件，对端消失时只会无限重发；设备离线再次停止也不能改变这一点。

本次不以设备在线标志作为终止依据：旧快照和重新注册都可能改变该标志，不能据此操作新会话。沿用不可变 inviteId、原 Call-ID/Dialog 和原代资源身份，增加有界终止：

1. 首次合法 Dialog 的 BYE 发送尝试之前，持久化 `byeFirstSentAt`；重试只刷新现有 `byeSentAt`，不延后首次时间。网络发送失败也保留这个已开始终止的事实。
2. 正常 2xx/481、设备主动 BYE 和 121 通知仍按原确认路径处理。
3. 从首次 BYE 尝试起等待 32 秒（默认 SIP T1=500ms 的 64*T1 窗口）。到期且同一代 RTP、SQL STATE 都已确认关闭时，原子记录 `byeTerminatedLocallyAt` 和原因 `BYE_WAIT_EXPIRED`，确认 BYE 清理步骤。此事实不等同对端 ACK，`byeAcknowledged` 保持 false。
4. 原子操作同时校验 STOPPING、当前清理 lease、原始记录 CAS、RTP/STATE 步骤和服务端时间；失败、未知媒体状态、SQL 未关闭、租约丢失不能跳过。成功后照常按身份删除 SIP，会话删除失败仍补偿，四步完成才释放 owner/SSRC。
5. 无 Dialog、错误 Call-ID/owner 等数据不一致仍报错/保留，不靠超时掩盖身份问题。只有完成合法发送准备的会话才有首次时间。
6. 迟到的首次 INVITE 2xx 如果重新打开终止流程，清空该次 BYE 的首次时间/本地终止事实，重新给予等待窗口；重复的旧 2xx 不重新打开。旧代任务与 ACK 不作用于新 inviteId。
7. 已有 STOPPING 记录没有首次时间时，由下一次正常 BYE 发送尝试建立起点，不做人工 Redis 修复、旧协议迁移或猜测时间；最多再等待一个窗口及后台调度退避。

32 秒是 BYE 等待策略，不是清理总时限；Redis/媒体/数据库不可用仍需等待真实资源清理，后台退避也可能延后完成时间。SIP 规范区分本地会话结束与远端响应，本次明确记录两者，不伪造对端确认。

## 执行计划

1. 补失败回归：对端不响应/发送异常、窗口前不可释放、RTP/STATE 未完成不能释放、重复停止与旧代事件。
2. 实现持久事实、租约/CAS 原子终止和编排接入，不调整其他已发现的工具/截图问题。
3. 运行定向、全量 Java 回归和隔离真实 Redis 验证，检查重启后首次时间不变及新 owner 隔离。
4. 提供新构建供用户部署；当前运行实例不会随源码修改变化，不热替换、不擅自重启共享服务。
5. 新版本部署后，先让后台回收上次残留，再重跑 10 台无 BYE 退出、重新注册点播、迟到事件及最终跨层核验。

## 真实环境验收与风险

只使用自有模拟设备和精确 inviteId。强制终止的是模拟器，不是 WVP/ZLM。不能手工清空 Redis/SQL、删除设备来制造通过。至少核对 Invite、owner、清理 job/lease、SIP V2、SSRC 预留、ZLM listener/media 和 SQL epoch/stream。正常 CLOSED 摘要保留不属于活动残留。

短时网络故障可能导致对端未收到 BYE；本地会话仍必须有界结束。只有媒体关闭已核验时才释放本地关联，远端停止能力应另行通过真实设备断网/恢复验证。完整进程故障注入仍要求独立部署。

### 新发现：BYE 时间基准混用

10:49:25～10:49:27 通过同一只读连接连续执行 Redis `TIME` 三次，并记录本机请求前后时间，Redis 比 WVP 主机慢约 80.560 秒，往返仅 0.23～0.71 毫秒，不能用网络延迟解释。

源码核对：`InviteRepository.byeSent()` 用 `System.currentTimeMillis()` 保存首次时间，`terminateByeLocally()` 的 Java 预检查也使用 JVM 时间，而 `LOCAL_BYE` Lua 用 Redis `TIME` 校验到期。因此实际等待会被时钟偏差拉长；如果偏差相反，Java 预检查虽能阻止当前实例提前结束，但分布式/重启后的时钟变动仍不能用当前混合时钟模型可靠推导等待窗口。

此项是本轮真实部署发现的剩余风险，不能标记为已解决。彻底方案是使首次 BYE 起点、到期判定及本地终止时间使用同一 Redis 时钟，由 Lua 原子建立首次时间，Java 不再跨时钟判定到期；记录格式还应明确时钟语义。不能通过手工回拨共享机器时钟或放宽验收阈值掩盖。本轮先完成现版本实际行为观察，不现场修改生产代码。
