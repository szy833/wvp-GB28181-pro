# Invite 生命周期统一改造实施与验收

## 1. 实施范围和当前边界

本次按《Invite生命周期并发故障根因与统一改造方案》实现新协议，不以继续增加全局 Hash 的 WATCH 重试次数解决问题。

本轮只修改源码、测试和文档，执行离线及隔离 Redis/H2 验证。不部署、不重启 WVP/ZLM、不修改运行环境的 Redis 或数据库，也不清除此前通道 309、311 的残留证据。不包含 Git 提交。

离线通过不能替代设备、ZLM、数据库和 WVP 的实际部署验收。首次部署必须先排空旧会话并执行对应数据库迁移，不能直接覆盖运行包后启动。

后续用户已单独授权部署前排空、备份和数据库迁移。2026-10-11 20:17 已完成实际 MariaDB 迁移及基线复核，WVP 尚未启动；过程和备份位置见 [部署前排空、备份与迁移记录](2026-10-11-Invite生命周期部署前排空备份与迁移记录.md)。本段更新不改变本轮源码回归与真实端到端验收的区别。

## 2. 新协议和代码职责

| 组件 | 职责 |
|---|---|
| `InviteRepository` | 原子认领、主记录/owner/索引维护、状态约束、提交结果确认、终态保留 |
| `InviteStreamServiceImpl` | 有索引查询、独立 SIP/媒体事实、按 inviteId 协调等待者、建立到期处理 |
| `PlayServiceImpl` | 实时点播/回放/下载的统一创建、激活和停止编排 |
| `PlatformServiceImpl` | 广播接收 Invite 接入相同身份和清理协议 |
| `InvitePlayProjectionStore` | 数据库播放投影的持久化代次栅栏 |
| `InviteInfoCleanupStore` | STOPPING 主记录、清理租约、独立阶段确认和退避 |
| `InviteInfoPendingCleanupTask` | 独立清理 worker，调度线程仅提交工作 |
| `InviteInfoCleanupTask` | 有界轮转探测 ACTIVE 的精确媒体状态 |
| `InviteSnapshotService` | 有界独立截图 worker，失败或队列满不改变播放结果 |

生命周期：

```text
PREPARING -> WAITING_MEDIA -> ACTIVATING -> ACTIVE
    |             |              |          |
    +-------------+--------------+----------+-> STOPPING -> CLOSED
```

`sipAccepted`、`sipSessionConfirmed`、`sipReady`、`mediaArrived` 是独立事实，不能再用 `status=ok` 判断可播放。收到 SIP 200 OK 先持久化接受的 Dialog；只有 `SipInviteSessionManager.put()` 明确返回成功，才记录会话提交确认；SDP/SSRC/TCP 主动收流处理完成后才记录 sipReady。任何一个环节失败或被 STOPPING 拒绝，都走失败和完整清理，不调用建立成功回调。媒体提前到达不能绕过这个确认屏障。四项事实齐备、完成本代数据库投影和 Redis ACTIVE 提交后，才向等待者返回点播成功。旧 status 字段仅用于已有 DTO 表示，不作为新协议状态机。

创建顺序为：认领 inviteId/业务槽位、分配并持久化 SQL epoch、预留投影、保存 RTP 计划、创建/绑定 RTP、保存 SIP Call-ID/发送意图、发送 INVITE、分别确认 SIP/媒体、激活投影和主记录。平台广播也必须经过 ACTIVATING，不能从 WAITING_MEDIA 直接跳到 ACTIVE。

同槽位重复请求加入当前 owner，不重复创建 listener 或发送 INVITE。PLAY 以通道定义槽位；PLAYBACK/DOWNLOAD 加入录像时间窗口，不将同通道不同时间窗口强行互斥。STOPPING 不重新开放给新请求，完成清理后才释放槽位。

## 3. Redis 数据和提交语义

命名空间为 `WVP:INVITE:<serverId>:`，不读取旧 `VMP_GB_INVITE_*` Hash/索引、不双写、不回填、不恢复旧快照。

| 后缀 | 类型 | 用途 |
|---|---|---|
| `DATA:<inviteId>` | String | 完整主记录，包含精确资源绑定和必要 SIP 路由/对话快照 |
| `OWNER:<businessSlot>` | String | 当前业务 owner |
| `ACTIVE` | Set | 所有非 CLOSED 记录，包括 STOPPING，不等于可播放数量 |
| `PLAYING:<mediaServerId>` | Set | ACTIVE 播放记录，重复 Hook/激活不重复计数 |
| `SSRC_RESERVATIONS:<mediaServerId>` | Hash | 已落盘资源计划的 SSRC，直到 CLOSED 才释放；重启后参与分配对账 |
| `INDEX:STREAM/CHANNEL/DEVICE/MEDIA/SSRC/CALL:<value>` | Set | 精确查询索引 |
| `DUE` | ZSet | 建立超时和终态摘要清理时间 |
| `RECONCILE` | ZSet | 持久化轮转对账位置 |
| `PENDING` | ZSet | 清理重试时间，不设置待办 TTL |
| `JOB:<inviteId>` | Hash | BYE、SIP、RTP、STATE 独立完成标记 |
| `LEASE:<inviteId>` | String | 清理 worker 的短租约，不代替资源/SQL 身份校验 |

Lua 写前检查 key 类型，按本条主记录原始字节进行 CAS，同时维护派生数据，不再 WATCH 全局 Invite Hash。写结果区分 APPLIED、ALREADY_APPLIED、OWNER_CHANGED、STATE_CONFLICT、NOT_FOUND、COMMIT_UNKNOWN。响应丢失后必须读回精确提交内容确认；无法确认时禁止继续报告成功。

身份和代次不可被通用 metadata 更新替换。初始提交未确认时不创建外部资源；调用中 Redis 持续不可用时仍本地完成失败等待者，已提交主记录的持久化 deadline 在存储恢复后驱动清理。

主记录不使用 Redis TTL 直接消失。CLOSED 摘要和 Call-ID 保留 24 小时，以接收迟到 SIP 200 OK；下载结果公开查询保留 15 分钟，保留结果不代表 RTP/SIP 仍然活动。终态到期由有界任务原子清除主记录及保留索引。

部署支持单机/Sentinel Redis。Redis Cluster 多 key 脚本未做 hash slot 设计，启动前置检查明确拒绝，而不是运行中退回旧协议。

## 4. 代次身份和停止语义

本轮实际发布流为 `gb_<inviteId去掉连字符>`；多端口 RTP listener 为 `<8位SSRC十六进制>_<32位Invite十六进制>`。原设备/通道组合只作为业务定位信息。播放方使用 start 响应返回的实际 URL/stream，不能自行拼接旧流名。

按代唯一的流不会被上一代的注销 Hook 命中。缺少 originUrl 的注销还必须确认精确媒体已不存在；探测失败/超时是未知，不当作不存在。

实时停止接口仍为 `/api/play/stop/{deviceId}/{channelId}`，新增可选 `stream` 参数。已取得本轮 stream 的客户端应始终传入，例如 `?stream=gb_...`，旧代请求只定位旧代资源，不停止新代。未传 stream 表示明确停止该通道当前 owner；这种无身份的管理命令无法区分用户是否在重试旧请求，不应当作代次绑定关闭使用。通用通道当前停止入口也是当前 owner 语义。

压测工具记录 start 返回的实际 stream，stop 自动带上该参数；媒体计数和清理范围显式学习本次 stream。HTTP 响应丢失时，只从测试设备收到的 SSRC、严格格式 listener 和相匹配的 originUrl 学习本代流，不以所有 `gb_` 流为测试范围。

停止 API 的成功响应表示停止请求已受理，不等于异步 BYE 和所有资源已确认清理。验收必须继续查询待办及资源，不能以 HTTP 200 作为 CLOSED 的证明。

媒体不存在自动拉起入口不能用旧代 URL 重新创建另一代；需要重新调用 start 获取新 URL。HTTP 等待超时只结束该请求，不按通道停止其他请求正在等待的共享会话，建立超时由生命周期 deadline 收尾。

## 5. 清理确认和故障恢复

停止先提交 STOPPING，再依次尝试独立步骤，未完成不能删除主记录或释放 owner：

1. BYE：保存发送时间和可重试 Dialog；已发送不等于完成，收到成功响应或 481 才确认。设备主动 BYE 不反向重复发送。
2. SIP：BYE 完成后删除本 inviteId/Call-ID 的会话和索引，删除失败保留待办。
3. RTP：按 resourceId、媒体节点、listener 和实际流关闭，查列表/探测确认不存在后才确认并释放 SSRC。当前进程仍在执行创建时，即使业务 deadline 已过也不提前释放。
4. STATE：按 ownerId/epoch 关闭数据库投影，失败不阻塞其他独立步骤，但阻止最终 CLOSED。

四项均完成并持有有效租约时才 CLOSED。重启后从 PENDING 重新认领，不依赖进程内旧快照。已关闭后首次收到迟到 SIP 接受或 RTP 创建返回，只重新打开清理待办，不恢复 ACTIVE、不抢回新 owner。必要设备/平台路由快照不含密码，删除设备也不丢失已知 Dialog 的重试路由。

SSRC 自动分配对账包含已落盘资源计划，避免 WVP 重启后 ZLM 尚无可播放流时重复分配。资源创建结果未知、ZLM 不可达、BYE 没有回复、SQL 不可用时，允许 STOPPING 持续保留；不能为了让数量归零而丢弃待办。

清理每批最多 100 条、批间检查时间预算；轮转探测每批最多 100 条、已检查记录至少 30 秒后再探测。预算不能取消一个已经发出的外部请求，因此媒体 API 的超时仍是实际单轮耗时上界的重要组成。

Redis 数据丢失、跨系统请求被远端无限延迟、硬盘/持久化损坏不是 Lua 可回滚的事务范围。上线须配置持久化、备份、合理内存策略与故障告警。不能通过本轮离线测试宣称任意故障下零丢失。

## 6. 数据库迁移和一次性切换

通道增加 `play_generation_seq`、`play_owner_epoch`、`play_owner_id`、`play_owner_state`。allocateEpoch 使用事务行锁递增计数；reserve/activate/close 均按 owner/epoch 条件写入，关闭后保留代次水位。旧 start/stop 即使在新一代停止之后才执行，也不能复活旧状态。

目录单条更新、批量更新、通知更新及三个 upsert provider 不再写运行时 stream_id；公共通道无 owner 更新只允许非 GB28181 数据类型，避免目录同步绕过栅栏。

已有库选择对应升级脚本，不重复执行初始化脚本：

- `数据库/2.7.4/更新-mysql-Invite生命周期.sql`
- `数据库/2.7.4/更新-postgresql-kingbase-Invite生命周期.sql`
- `数据库/2.7.4-h2/更新-Invite生命周期.sql`

切换步骤：停止新点播入口、按旧版本排空并确认 SIP/listener/媒体/数据库状态、备份旧命名空间和有效下载结果、备份数据库并执行迁移、部署新代码、使用新的空 Invite 命名空间验收。未执行迁移时启动直接失败并提示，不启动后再发现点播 SQL 缺列。

已有异常残留必须在核实无实际会话后受控修复，本轮不执行。禁止 FLUSHDB 或启动时无条件清空全部通道 streamId。回滚同样必须排空，旧包不能读取新协议会话。
