## 1. 范围与现场边界

2026-10-14 对 18080 无响应的现场诊断确认：Java 21 虚拟线程在 `RtpResourceContext.close()` 的同步 monitor 内执行日志、媒体 HTTP 清理，16 个 carrier 持续 pinned，导致 HTTP 调度饥饿及连接积压。堆和 GC 证据不支持内存耗尽。具体证据及未还原的最初锁交错见 [18080 无响应初步排查](2026-10-14-18080无响应初步排查.md)。

## 2. 修复设计

- `RtpResourceContext` 使用 `ReentrantLock stateLock` 协调状态认领和鉴权 owner 更新。Java 21 虚拟线程等待此锁时可以卸载 carrier，不再使用 `synchronized(context)`。
- 状态日志、成功/失败清理、业务回调都在状态锁外执行。`close()` 使用独立的 `ReentrantLock closeLock` 串行关闭和清理：第一个调用认领 CLOSED 后执行清理；重复关闭等待该清理返回，再返回 false。不能仅因已经读到 CLOSED 就提前报告重复关闭已完成。
- 服务层的鉴权写入、比较迁移、终止时比较删除统一使用 `context.withAuthLock(...)`，保持 Redis 操作和内存 owner/key 更新与终态转换互斥。写入期间终止需等待；终止认领后拒绝迟到鉴权写入。原有 owner 比较脚本不变，不改变 Invite/SIP 的代次或清理协议。
- `lifecycleLock` monitor 只负责任务/Hook 登记和清理快照。迟到登记的 `stop`/`removeSubscribe` 移到 monitor 外执行，仍使用原 owner 句柄回滚。
- 不更改 JDK、日志依赖、虚拟线程开关、Tomcat 连接上限或媒体 HTTP 超时设置。

`withAuthLock` 仅用于鉴权操作与状态协调；不要在其回调中调用 `close()` 或业务回调，避免引入 `stateLock -> closeLock` 的反向锁序。现有关闭路径为 `closeLock -> stateLock`，状态锁释放后才执行媒体清理。

状态日志不再构成串行屏障；并发转换的日志输出顺序可能与实际状态认领顺序不同。判断终态以状态/owner 为准，不能依赖日志行的先后次序。

## 3. 自动回归

### 3.1 先复现再修复

- 旧代码上 `closeCleanupDoesNotHoldContextMonitor` 失败，确认外部清理持有 context monitor。
- 独立 JVM 限制虚拟线程 scheduler 的 parallelism/maxPoolSize 均为 1，用受控 `ReentrantLock` 模拟慢清理或日志写锁。业务线程进入阻塞点后，另起虚拟线程模拟健康请求，要求 2 秒内取得执行机会。旧关闭实现出现 carrier 饥饿。
- 日志测试使用 `UnsynchronizedAppenderBase`，匹配实际 `OutputStreamAppender` 基类，不额外引入测试自身的 monitor。修正测试替身后临时恢复生产日志 monitor，两个日志场景均如期失败；随后移除临时 monitor，再运行绿色回归。
- 迟到 Hook/任务回滚的单 carrier 测试在回滚仍处于 `lifecycleLock` monitor 内时均失败；移出后通过。
- 服务层旧实现上鉴权写入、迁移、媒体关闭的 monitor 检查均失败；修复后通过。
- 重复关闭测试保证首次慢清理期间第二次关闭仍等待，清理只执行一次；原有鉴权迁移与终态互斥测试改用共享鉴权锁验证同一行为。
- 补充服务层写入/迁移暂停与关闭并发的两个 latch 用例，验证关闭等待、终止清理读取最新鉴权 key/owner、只清理一次。临时移除 `withAuthLock` 的锁做 mutation 验证时，两例都因关闭提前返回而失败；已恢复锁并通过最终回归，记录为 `target/rtp-auth-serialization-red.log`。

## 4. 待集中执行的真实环境验收

在隔离或获准的预发布环境执行，不在保留的故障现场继续升压：

| 场景 | 观测与通过条件 | 风险 |
| --- | --- | --- |
| 300 路点播后并发停流，多轮重复 | 持续请求版本/健康接口，记录延迟；线程快照/JFR 中无 RTP monitor 导致的 carrier 耗尽；连接/CLOSE_WAIT 能回落 | 会创建大量真实 SIP、RTP、SSRC 和 ZLM 资源，必须有残留对账和停止流程 |
| 慢日志输出或日志写锁竞争 | 健康请求仍可调度；RTP 状态与 owner 最终一致 | 日志仍是同步写入，慢日志会延迟对应业务，不能由本修复推断所有日志路径无阻塞 |
| ZLM 慢响应、网络断连、超时 | 不耗尽 carrier；依赖恢复后清理推进，资源状态可对账 | 本修复未增加端到端截止时间/有界执行通道，单次清理仍可能慢，重复关闭按约定等待 |
| Redis 慢响应，鉴权写入/迁移同时关闭 | 新写入在终止后被拒绝；迁移与终止互斥；旧 owner 清理不删除新 owner 鉴权 | 同一资源的状态转换会等待正在执行的 Redis 操作，需验证客户端超时和恢复后的补偿 |
| 媒体早到、迟到 Hook、超时与关闭并发 | 仅获胜转换执行其清理/回调；无任务/Hook 句柄泄漏，旧代事件不影响新代 | 需结合 Invite/SIP/媒体完整链路，不能只看 HTTP 停止成功 |
| 重复关闭、快速同流重开 | 重复关闭不在首轮关闭清理前返回；旧 context 不关闭新 owner listener/业务流 | 必须同时检查 Redis Invite/鉴权、ZLM listener/流、SSRC 和 SIP V2 状态 |

部署前先按项目生命周期迁移约定排空会话，备份配置并确定回退路径。实际部署和恢复需单独获得用户授权。浏览器内存受限的多分屏容量测试应在控制面恢复并完成上述停流验收后安排，本地回归不提供视频路数上限结论。
